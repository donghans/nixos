# donghans-doc-rigor — 조사 종합 문서 작성 + 무맥락 검증

## 0. 언제 쓰나
- 한 대화에서 긴 조사·논쟁·여러 번의 정정을 거쳐 뭔가를 알아냈고, 그 결론으로 **구현에 착수하기 전**.
- 그 조사 내용이 **이 대화 밖의 누군가**(다음 세션, 다른 개발자, 미래의 자신)에게도 필요하다 — 한 번 묻고 끝날 지시가 아니라, 나중에 "왜 이렇게 했지"를 되짚을 근거가 돼야 한다.
- 사용자가 명시적으로 "문서로 남겨" "기록해" "검증도 해 줘"라고 요청했거나, 작업 성격상(여러 설계 문서에 걸쳐 연쇄로 영향이 퍼지는 변경, 운영 인프라 변경, 되돌리기 비싼 결정) 당연히 남겨야 할 때.
- 구현 **계획**을 세우고 구현 전에 검증받는 일은 `donghans-plan` 스킬이다(검증자 프롬프트 틀·순서 규칙은 거기). 이 스킬은 조사 결과를 설명 문서로 남길 때.
- **작은 수정 한두 줄짜리 커밋 메시지나, 세션 재개용 인수인계(donghans-handoff)에는 안 쓴다** — 이건 그보다 무겁고 오래 남는 기록이다.

## 0. 문서를 어디에 두나
- **팀(다른 개발자·고객)이 읽어야 하는 문서**(제품·명세·결함·결정): 프로젝트 저장소의 추적되는 문서 디렉터리. 커밋한다.
- **개인 작업 문서**(내 조사·계획·검증 기록 등 git 이 추적하지 않을 것): 프로젝트 폴더나 `.gitignore`·`.git/info/exclude` 로 가려진 폴더가 아니라 **`~/ctx`** 에 `donghans ctx doc propose <plan|qa|note> <이름>` 으로(`donghans-ctx` 스킬). 이 경우 아래 「커밋하기 전」은 「제안을 반영하기 전」으로 읽고, 검증 에이전트에게는 `donghans ctx doc read` 로 읽게 한다(경로 대신 `--project`·종류·이름을 준다).
- 어느 쪽인지 모르겠으면 사용자에게 한 줄로 묻는다. 사실이 팀에 필요한데 개인 문서에만 두는 것도, 개인 메모를 저장소에 올리는 것도 피한다.

## 1. 문서를 쓸 때 지킬 것

### 1-A. 영점에서 읽혀야 한다
처음 읽는 사람은 이 대화를 전혀 모른다. 다음을 지킨다.
- 등장하는 모든 고유명사·약어·시스템 이름(프로젝트 안 요구사항·문서 번호, 외부 서비스 이름, 내부 도구 이름 등)은 **처음 나오는 자리에서** 한 문장으로 설명한다. 뒤에 가서야 설명되는 "선행 참조"를 만들지 않는다 — 각주·절 번호로 미루더라도 그 사실만은 먼저 알려준다("요구사항 번호가 뭔지는 §5에서 자세히 다룬다" 정도).
- "일어난 일"(조사해서 알아낸 사실·이력)과 "하기로 한 일"(계획)과 "아직 안 정해진 일"(열린 질문·외부(고객·타 팀) 결정 대기)을 **서로 다른 절로 분리**한다. 셋을 한 문단에 섞으면 다음 사람이 "이미 끝난 건지 아직 결정 전인지" 헷갈린다.
- 범위 밖(이번에 안 본 것·확인 못 한 것)을 명시한다. 안 적으면 "다 봤다"로 오인된다.

### 1-B. 근거 등급을 사실마다 붙인다
이 세션이 쓴 모든 사실 주장에 확인 방법을 표시한다. 등급 이름은 프로젝트 관례가 있으면 그걸 따르고, 없으면 아래 기본값을 쓴다.

| 등급 | 뜻 |
|---|---|
| 직접확인 | 이 세션이 직접 명령을 돌리거나 파일을 읽거나 API를 불러 확인함 |
| 에이전트조사 | 하위 에이전트가 조사해 보고했고, 이 세션이 핵심 1~2건만 표본으로 재확인함 |
| 미재확인 | 에이전트·문서의 보고를 그대로 실었고 재확인 안 함 |

파일을 인용할 때는 **경로:줄번호**와 (짧다면) **원문 그대로**를 같이 적는다. "~라고 적혀 있다"를 의역으로 쓰고 큰따옴표를 붙이면 안 된다 — 직접 인용처럼 보이는 문장은 실제로 그 글자 그대로여야 한다. 의역이면 "요지"라고 표시한다.

이렇게 등급을 매기는 이유: 조사 중간에 "문서에 그렇게 적혀 있어서" 결론 낸 것을 나중에 코드로 보니 틀렸던 일이 실제로 있었다(겉보기엔 확정처럼 읽히는 서술이 실은 검증 안 된 추정이었던 경우) — 등급이 없으면 다음 사람이 그 구분을 못 하고 틀린 전제 위에 일을 쌓는다.

### 1-C. 기존 관례를 재사용한다
그 프로젝트에 이미 결정·질문을 모아 두는 문서(예: 결정 로그, 열린 질문 목록)가 있으면 **형식을 베껴 쓴다** — 새 형식을 발명하지 않는다. 새로 쓰는 조사 종합 문서와 기존 결정 로그 사이에 역할을 나눈다: 조사 종합 문서는 "왜·어떻게 알아냈는지"의 배경이고, 결정 로그는 "무엇을 묻고 무엇이 기본값인지"의 살아있는 상태다. 조사 문서에서 결정 로그로 가는 참조는 한쪽 방향으로 — 결정 로그가 최신 상태(SoT)이고 조사 문서는 그걸 가리키기만 한다(복사해서 두 곳에 같은 내용을 유지하지 않는다 — 나중에 결정이 바뀌면 한쪽만 바뀌고 어긋난다).

## 2. 쓰고 나서 — 무맥락 검증

문서를 커밋하기 전(또는 커밋 직후, 되돌리기 쉬운 단계에서), **이 대화를 전혀 모르는 새 에이전트**를 띄워 그 문서 하나만 주고 검증시킨다.

- **반드시 새 에이전트(일반 서브에이전트)를 쓴다 — fork가 아니다.** fork는 이 세션의 맥락을 통째로 물려받아 "뭘 확인해야 하는지 이미 안다"는 상태로 시작하므로, "아무 맥락 없는 독자" 테스트가 안 된다.
- 프롬프트에는 **문서 경로만** 주고, "이전 대화를 모른다고 가정하고, 이 파일 하나만 읽고 시작한다"고 명시한다. 이 세션이 안 가진 정보(예: 외부 서버·다른 사람의 자격 증명이 필요한 것)는 "확인 불가"로만 적고 넘어가라고 미리 알려준다.
- 검증 에이전트가 할 일:
  1. **자기완결성** — 설명 없이 튀어나오는 용어·선행 참조가 있는지.
  2. **인용 대조** — 「직접확인」이라 표시된 것 중 의미 있는 표본(파일 경로·줄번호·원문 인용 10곳 안팎)을 실제로 열어서 정말 일치하는지 하나씩 확인. 추측하지 말고 열어 본다.
  3. **등급 일관성** — 실제로는 확인 안 된 건데 「직접확인」으로 과장돼 있는 곳이 있는지.
  4. **논리적 정합성** — 결론·작업 범위 절이 앞선 조사 내용에서 실제로 따라 나오는지, 비약·복사 실수(다른 항목 이름이 잘못 들어간 것 등)가 있는지.
  5. **오독 위험** — 다음 세션이 이 문서만 보고 범위를 넘어선 행동을 할 수 있는 문장, "완료"처럼 읽히지만 실은 "예정"인 서술.
  6. **종합 판정**: 그대로 신뢰 가능 / 정정 후 신뢰 가능(구체적으로 어디) / 신뢰 불가.
- **검증 결과를 코드 리뷰처럼 취급한다** — 지적된 걸 "참고하겠다"고 흘리지 말고 실제로 문서를 고치고, 고친 사실과 이유를 커밋 메시지에 남긴다. 심각도가 낮은 지적(등급 과신 등)도 빠르면 같이 고친다.

## 3. 비용 판단
이 전체 절차(종합 문서 + 무맥락 검증 에이전트 1개)는 하위 에이전트 시작 비용(3~4만 토큰)이 드는 일이다. 다음에 해당할 때만 한다 — 여러 설계 문서에 걸친 연쇄 변경을 앞두고 있을 때, 운영 인프라를 바꾸는 작업 직전일 때, 되돌리기 비싼 결정이 걸려 있을 때, 또는 사용자가 명시적으로 요청했을 때. 한두 줄짜리 정정이나 이미 끝난 작업의 단순 요약에는 과하다 — 그럴 땐 평소처럼 커밋 메시지·프로젝트 상태 문서 갱신으로 충분하다.
