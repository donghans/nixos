# donghans-card — 결정 카드 논의

**목표: 에이전트가 제안한 것을 사용자 결정처럼 쓰지 않고, 사용자가 실제로 한 말을 근거로 논의한다.** 카드 하나 = 사용자의 원칙·습관·결정 하나 + 근거 원문 + 반례. 설계·결정·이력: `donghans ctx doc read --project nixos plan llm-trust/02-card-skill-ui`.

## 절차
1. **인자 분리.** 인자(`ARGUMENTS`)에서 **카드 참조처럼 생긴 토큰만** 고른다: `프로젝트:uuid8`(uuid 앞 8자 이상, 16진 — 예 `nixos:3f2a9c1b`) 또는 `uuid8`. 나머지 자연어는 **쟁점**이다. **쟁점은 셸 명령에 넣지 않는다**(따옴표·`$()` 가 들어 있을 수 있다).
2. **카드 읽기(읽기 전용):** `donghans ctx card show <참조…>` (참조가 여럿이면 한 번에, 판 이력이 필요하면 `--history`). 목록은 `donghans ctx card list [--project P] [--state S]`.
   - 「일치하는 카드 0건」·「여러 건」이면 후보가 나온다 → 추측하지 말고 사용자에게 어느 것인지 묻는다. `프로젝트:` 를 생략했을 때 여러 프로젝트에 같은 앞자리가 있으면 이 경우다.
   - 이 머신에 저장소가 없는 프로젝트의 카드는 보이지 않는다(출력의 「건너뛴 프로젝트」). 그 사실을 사용자에게 말한다 — 「카드가 없다」가 아니다.
3. **출력을 읽고 먼저 확인할 것**(보고는 짧게, 문제가 있을 때만 길게):
   - 카드 상태 `draft`(에이전트 제안)·`reviewed`(사용자가 맞다고 확인)·`adopted`(반영됨)와 제안자(`proposer`).
   - 근거 줄 아래 `↳` 표시: **일치**(인용이 원문에 있음) · **⚠ 미일치**(인용이 그 메시지에 없음) · **⚠ 메시지 없음** · **⚠ 모호** · **포인터**(전체 본문을 읽을 때 채움) · 인용 없음. 미일치·메시지 없음은 사용자에게 먼저 알린다. 의심스러우면 `donghans ctx msg <uuid8>` 로 원문 전체를 읽는다.
   - 「형식 문제」·「상태가 unknown」 경고.
4. **쟁점이 있으면 쟁점에 먼저 답한다.** 카드를 처음부터 끝까지 다시 읊지 말고, 쟁점과 관련된 부분(내용·근거·반례)을 **인용해** 답한다. 쟁점이 없으면 카드 요약(제목·상태·제안자·근거 대조 결과·반례)을 말하고 무엇을 논의할지 묻는다.
5. **카드를 고치자는 결론이 나오면** 아래 「카드 수정」 절차를 따른다. 그전에는 아무것도 쓰지 않는다.

## 지켜야 할 규칙
**코드가 막는 것**(어기려 해도 거부되거나 자동으로 되돌려진다 — 그래도 이 사실을 알고 지킨다)
1. `draft` 는 **에이전트의 제안이지 사용자 결정이 아니다.** 사용자 결정처럼 쓰지 않는다. 근거 줄의 인용만 사용자 말이다 — `내용` 절은 해석이다.
2. 새 카드는 `proposer: agent`·`state: draft` 로만 만든다. `proposer: user` 나 `reviewed`·`adopted` 를 쓰는 제안은 거부된다(사람이 llmui 에서 한다). 상태를 올리자고 하지 않는다.
3. **이미 `reviewed`·`adopted` 인 카드의 내용을 고치면 저장소가 `draft` 로 강등한다**(`last_confirmed` 가 비워지고 이력에 한 줄이 붙는다). 고치기 전에 **그 사실을 사용자에게 먼저 말한다.**
4. 근거의 인용은 그 메시지의 실제 본문이어야 한다(`card show` 가 대조한다). 타 프로젝트 대화(remote 없는 프로젝트 — tot·genple 등)를 근거로 `nixos` 처럼 remote 가 있는 저장소의 카드에 쓸 때는 원문을 적지 않고 포인터 `- [msg:<uuid8>] (포인터 — 읽을 때 채움)` 로 적는다(인용하면 거부된다).

**문구로만 안내하는 것**(코드가 막지 않는다 — 어겨도 아무도 모를 수 있으니 특히 조심한다)
5. **카드를 고치는 제안은 차이(diff)를 보여 주고 사용자 확인을 받은 뒤에만** 한다.
6. 논의에서 나온 결정·맥락은 `## 이력` 에 한 줄로 더하고, 사용자가 한 말은 **정확히 인용하고 시점을 적는다**.
7. 모르는 것은 뭉개지 말고 묻는다. 카드에 없는 사용자 의도를 추측해 채우지 않는다. 사용자의 한정(범위·조건)이 붙은 말은 한정을 떼지 않는다.

## 카드 수정 (사용자 확인 뒤)
1. 읽은 판을 기준으로 **전체 본문**을 파일로 만든다(저장소 머리말 `<!-- ctx … -->` 는 넣지 않아도 된다 — 넣으면 `state` 를 `draft` 밖으로 바꾸는 제안은 거부된다).
2. **차이를 사용자에게 보여 준다**(바뀐 줄·이력에 더할 한 줄·강등 여부). 확인을 받는다.
3. `donghans ctx doc read note cards/<uuid 전체> --project <프로젝트>` 로 읽은 뒤(읽지 않은 문서를 덮어쓰는 제안은 거부된다), `donghans ctx doc propose note cards/<uuid 전체> --file <파일> --project <프로젝트>`.
4. 결과(`반영했다`·`거부`·`충돌`)와 가드의 알림(`강등했다` 등)을 사용자에게 알린다. 거부되면 이유를 그대로 전하고 고쳐서 다시 제안하되 우회하지 않는다.
   - 카드 문서는 beelink 에서만 반영된다. 노트북에서는 제안이 대기 상태로 남을 수 있다(`donghans ctx doc status`) — 그렇다고 알려 준다.

## 새 카드 만들기 (사용자가 요청할 때만)
1. 카드는 **근거가 된 대화의 프로젝트 저장소**에 둔다(`--project <그 프로젝트>`). 여러 프로젝트에 걸친 범용 카드는 `nixos`. uuid 는 `python3 -c 'import uuid; print(uuid.uuid4())'`.
2. 근거는 사용자 말만 — 메시지 전체 본문을 `donghans ctx msg <uuid8>` 로 읽고(긴 본문은 파일 경로가 나오면 `Read` 로 해당 구간을 정확히 읽는다) **원문 그대로** 인용한다. 반례를 **1건 이상** 적는다(없으면 「반례를 찾지 못함」이 아니라 왜 못 찾았는지).
3. 형식(필수: `id·title·kind·proposer`, 근거 1건 이상, 반례 1건 이상):
```
---
id: <uuid4 전체>
title: 한 줄 제목
kind: 대전제 | 습관 | 한정 결정 | 희망사항 | 관점
proposer: agent
applies_when: 적용 조건(한정 결정이면 범위를 여기에)
tags: [발언 당시 상태 등]
implemented_via: 지침 | 스킬 | UI | 코드 | 이미 있음(링크) | 미정
related: [프로젝트:uuid8]
last_confirmed:
---
## 내용
(해석 — 한두 문단)
## 근거 원문 (사용자 말만)
- [msg:<uuid8 이상>] "원문 그대로의 인용" (2026-11-06 17:39 KST · 세션 앞 8자)
## 반례·한계
- …
## 이력
- 2026-11-06 · 만듦 · agent
```
4. `donghans ctx doc propose note cards/<uuid 전체> --file <파일> --project <프로젝트>` — 사용자 확인 뒤. 새 카드는 `draft` 로 만들어진다.
5. 새 용어가 처음 나오면 그 자리에서 한 줄 풀이와 출처(누가·언제 만든 말인지)를 적는다(용어집은 만들지 않는다).
