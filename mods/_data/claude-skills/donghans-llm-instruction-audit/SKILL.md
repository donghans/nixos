# donghans-llm-instruction-audit — 모델에게 가는 지침을 점검하는 절차

LLM 에이전트 제품 한 곳의 작업에서 **놓쳤다가 뒤늦게 찾은 것들**을 점검 항목으로 고정한 것이다(사례 원문이 필요하면 그 프로젝트의 작업 기록 보관소를 본다). 한 사례에서 「지침서 문구가 이상하다」로 시작한 작업이 실제로는 코드가 만든 도구 설명·오류 문구·안전장치·모델 호환·시험 설계의 문제였다. **설계 단계와 진단 단계에서 아래 항목을 먼저 돈다.**

> 이 점검 항목은 한 프로젝트의 경험에서 나왔다. 각 항목은 **점검할 질문**으로 읽고, 답은 해당 프로젝트에서 직접 확인한다(항목 자체를 모든 환경에서 참인 사실로 취급하지 않는다). 처음 점검이 범위를 좁게 잡으면 다른 도구 계열에 같은 부류의 문제가 남을 수 있다(그 프로젝트의 관찰이며 모델 변경 요인은 분리하지 못했다) — 그래서 아래에 계열별 점검(§2-A)과 추적(§2-I)이 있다.

**적용 범위**: 도구 호출이 없는 단일 챗봇은 §1·§2-B(도구·생성 지침서 항목 제외)·§2-E·§2-F 가 주로 해당한다. 도구·에이전트 루프가 있는 제품에는 §2-A 의 계열별 덤프·§2-B 의 도구 관련 항목·§2-C·§2-D·§2-G 가, 지침서를 모델이 생성·조립하는 구조에는 §2-B 의 생성형 항목과 §2-H 의 「수정이 닿는 범위」가 추가로 해당한다. §2-I 는 모두에 해당한다.

용어: **하드 가드** = 코드가 결정적으로 차단하는 검사(모델의 말에 의존하지 않음). **그림자 모드** = 판정만 기록하고 차단하지 않는 상태. **장부** = 이미 한 호출을 기록해 중복 실행을 막는 저장소(예: 호출 기록, 멱등 키 저장소). **지침서** = 모델에게 주는 사전 작성 문서, **런타임 지시** = 호출 때 코드가 덧붙이는 공통 지시, **감독자 메시지** = 에이전트 루프가 끼워 넣는 시스템 메시지(예: 재시도·교정 안내).

## 0. 언제 읽나
- 프롬프트·지침·도구 정의·오류 문구·에이전트 루프(감독자·교정 턴·재시도)를 새로 만들거나 고칠 때.
- 모델·제공사를 바꾸거나 더 작은 모델로 비용을 줄이려 할 때.
- 「모델이 지시를 안 따른다」「포기한다」「같은 지시에 결과가 모델마다 다르다」「성공이라는데 결과물이 없다」를 진단할 때.
- 별도 판정 모델이나 판정 전용 API 를 어디에 쓸지 정할 때.
- `donghans-plan` 으로 이런 변경의 계획을 세울 때(계획서에 §2-A 의 덤프 결과를 첨부하고, 검증자에게도 같은 덤프를 읽게 한다).

## 1. 핵심 원칙 (순서대로 지킨다)
1. **모델이 실제로 받는 입력 전체를 한 곳에 모아 처음부터 끝까지 읽는다.** 코드를 grep 해서 「지침서에는 이 문구가 없다」고 결론내리지 않는다. 모델은 지침서 + 런타임 지시 + 도구 목록과 설명 + 도구 스키마 + 앞 턴의 도구 응답·오류 문구 + 시스템이 끼워 넣은 감독 메시지를 **한 덩어리**로 읽는다. 각각은 멀쩡해도 이웃한 문장끼리 모순일 수 있다.
2. **추정과 확인을 문서에서 구분해 쓴다.** 「~로 읽힌다」는 원문을 대조하기 전에는 원인으로 적지 않는다. 모델 내부 판단은 보통 조회할 수 없으므로 **모델이 쓴 사유 문구와 입력의 글자 일치**는 가설을 지지하는 증거일 뿐 확정이 아니다(수정 뒤 행동 변화가 있으면 더 강해진다). 정정이 생기면 이력으로 남긴다.
3. **판단이 필요한 것과 결정적으로 확인되는 것을 나눈다.** 「저장 도구가 성공했는가」는 장부·반환값으로 코드가 확인한다(하드 가드). 「출력 내용이 충분한가」「이 오류가 고쳐서 풀리는가」는 판단이라 모델·규칙·판정 API 중 무엇을 쓸지 가설로 둔다.
4. **강한 모델 한 개의 통과는 증거가 아니다.** 강한 모델은 문구의 모순을 조용히 해소해 결함을 가릴 수 있다. 작은 모델·다른 제공사에서 드러나는 경우가 많다. 모델별 결과는 같은 입력으로 비교한다.
5. **검증되지 않은 외부 서비스(판정 API 등)의 사용 방식은 정론으로 저장하지 않는다.** 가설 목록(가설·근거·반증 조건·상태)으로 두고 시험으로 상태를 바꾼다.
6. **문구는 확률적이다 — 어기면 안 되는 규칙은 코드가, 안내는 문구가 맡는다.** 어겼을 때 데이터 유실·거짓 성공·중복 실행·고아 작업이 생기는 규칙은 코드 게이트(거절·차단)가 본체이고, 문구는 거절 뒤 복구법을 알리는 층이다. 문구로만 둔 안전 규칙은 「가설」로 적는다. 같은 주제의 문구를 두 번째로 고치는 중이거나 약한 모델이 문구를 어긴 기록이 있으면 코드로 올릴 후보다. 목표는 문구가 틀려도 피해가 한정되는 구조다.

## 2. 점검 절차

### A. 입력 덤프를 만든다 (모든 점검의 출발점)
- 한 호출(에이전트 한 단계)에 대해 모델이 받는 것을 **조립 결과 그대로** 한 파일로 출력하는 수단을 만든다(프로젝트에 없으면 §3). 포함: 시스템·지침서·런타임 지시, 도구별 이름·설명·스키마(모델이 보는 이름 형식 그대로), 대표 오류·거절 응답 문구, 감독자 메시지 템플릿.
- 덤프를 **소리 내어 읽듯** 처음부터 끝까지 읽고 B 를 점검한다. 검증자(무맥락 에이전트)에게도 이 덤프를 읽게 한다.
- **덤프는 도구 의미 계열마다 만든다.** 같은 문구(「그대로 넘긴다」「나누어」「줄여」「한 번만」)가 계열마다 다른 뜻으로 작동한다. 계열 예: 본문이 호출 인자 자체인 기록형 / 지시와 자료가 분리되고 결과물을 통째로 다시 만드는 편집형 / 작업번호만 즉시 주고 나중에 끝나는 접수(비동기)형 / 읽기형 / 승인형(제품마다 다르다). 점검 기록에 「덤프한 계열 / 안 한 계열(미점검)」을 적고, 안 한 계열에는 결론을 확장하지 않는다(계획서 범위도 「계열 X 한정」으로 적는다).
- **교차표**: 규칙 주제(그대로·나누기·줄이기·재시도·제출/포기·한 번만)마다 모든 출처(지침서·런타임 지시·도구 설명·스키마·오류·감독자 메시지)의 문장을 덤프에서 검색해 한 표에 모으고, 계열별로 뜻이 달라지는 칸을 표시한다. 문구를 고치기 전 같은 주제의 기존 문장을 확인하는 수단이기도 하다.

### B. 문구 점검
- **모순·긴장**: 같은 문단·인접 문장에 「한 번만/다시 시도/다시 호출하지 않는다/반드시/절대」가 섞여 있지 않은가. 서로 다른 경우(명확한 거절 vs 시간 초과)를 말하는 규칙은 **경우를 이름 붙여 분리**한다.
- **코드가 만든 문구가 지침서와 어긋나지 않는가**: 도구 설명의 「한 번만 실행된다」, 지침서의 「그대로 넘긴다」 같은 가드와 예외 대응(「줄이거나 나눈다」)의 충돌. 지침서를 모델이 생성하는 구조라면 가드와 예외를 같은 절에서 연결하게 한다.
- **손실을 부르는 어휘**(줄여·핵심만·요약·짧게·생략)를 교차표에서 찾는다: 사실 삭제로 읽히지 않는가. 무손실 대안(나누기·인자 밖 참조로 넘기기)을 함께 안내한다.
- **모델이 긴 자료를 인자로 베껴 써야 하는 경로**가 있는가: 인자 길이·출력 한도·타임아웃·반복 감지로 인자가 잘릴 수 있고, 「그대로 전달」 가드가 그 경로를 부추긴다. 긴 자료는 인자 밖(참조·별도 필드)으로 둘 곳을 만든다.
- **오류 응답이 상태를 말하는가**: 검증 거절은 「아직 아무것도 만들어지지 않았다 — 고쳐서 다시 호출해도 된다」, 불확실 상태는 「결과를 확인할 때까지 다시 부르지 않는다」. 상태를 모르면 모델은 보수적으로 포기한다.
- **모델이 허용 도구 목록을 아는가**: 도구를 전부 노출하고 허용 여부는 호출 때 검사만 하는 구조(예: 서버가 모든 도구를 노출하는 경우)면, 프롬프트에 허용 목록(모델이 보는 이름 = 내부 id)을 싣고 거부 응답에도 싣는다.
- **오류 복구·재시도 규칙은 생성 지침서에 맡기지 않는다.** 모델·생성 결과에 따라 갈리는 판단은 코드가 실행 때 붙이는 런타임 지시(지침서보다 우선한다고 명시하되, 우선순위 문구만으로 모순을 덮지 않는다 — 어기면 피해가 큰 규칙은 하드 가드가 본체이고 문구는 복구 안내다 — 원칙 6)로 둔다. 이는 위 「경우를 이름 붙여 분리」를 적용한 결과를 **어디에 두는가**에 대한 규칙이다(분리는 문구의 문제, 위치는 층의 문제).

### C. 안전장치와 문구의 상호작용
- 중복 방지 장부·승인·호출 예산이 **정상 호출까지 막지 않는가**: 병렬 호출(같은 턴의 형제 호출), 진행 중(수십 ms)과 결과 불확실(오래된 시도)의 구분, 거부된 호출도 예산을 쓰는가, 거부 문구가 모델이 복구할 수 있게 쓰였는가.
- 도구가 시간 제한에 걸렸을 때의 규칙(재호출 금지·성공 미확인이면 완료 금지)과 일반 오류 복구 규칙이 충돌하지 않는가.
- **접수(비동기)형 도구가 있다면**: 접수 응답의 「이 턴을 마친다」가 지침 끝의 「제출 전에는 끝난 것이 아니다·할 수 없으면 포기」와 충돌하지 않는가. 접수 중 완료·포기 제출을 문구가 아니라 게이트가 거절하는가, 포기·실패 때 접수된 작업이 고아로 남지 않는가.

### D. 거짓 성공 방지
- 「완료」 제출을 모델의 말로만 받지 않는다. 저장·전송 단계는 **성공한 도구 기록이 있어야** 완료로 받는 하드 가드를 둔다. 내용 판별은 별도 층(결정적 대리 지표 → 별도 판정 모델 → 같은 모델의 자기 점검은 최후)이며 **그림자 모드**로 데이터를 모은 뒤 차단으로 올린다.

### E. 모델·제공사 호환과 비용
- **모델 ID**: 별칭(`model-x`)과 서버에 등록된 ID(`model-x-YYYYMMDD`)가 다를 수 있다. 목록을 조회해 확인한다.
- **추론(thinking/effort) 파라미터**: 모델별로 허용 값이 다를 수 있다(일부 값을 거부하는 모델이 있을 수 있음). 제공사 문서와 실제 호출로 확인하고, 모델 단위 호환 표를 두고 일괄 적용하지 않는다.
- **가격·한도 표**: 신규 모델이 표에 없어 기본 요금표(fallback)로 계산돼 과금이 틀어지지 않는지(입력·출력·캐시, 제공사별 가격 구조 — 예: 길이 구간제 — 포함), 컨텍스트·출력 한도 표에 항목이 있는지 확인한다. 가격은 **공식 페이지**를 직접 조회한다(제3자 블로그만 믿지 않는다).
- 다중 모델 활성화(관리자 설정·정책 상수·조직 허용)는 층이 여럿이다 — 어느 층이 막는지 에러 문구로 구분한다.

### F. 시험 설계의 함정
- **옛 산출물을 복사해 시험하지 않는다**: 생성 규칙·제품 수정이 반영된 **새 산출물**로 시험한다(옛 시험이 지금 제품이 만들지 않는 시나리오를 재고 있을 수 있다).
- **상태 공유 간섭**: 연속 실행이 같은 문서·파일·장부를 공유하지 않는가(앞 실행의 백그라운드 작업이 다음 실행을 막음). 간섭이 있으면 그 실행은 모델 비교에서 뺀다.
- **환경이 모든 모델을 실패시키는 시나리오**는 모델 비교의 근거가 아니다(시간 제한 초과 등). 먼저 시나리오를 분리한다.
- **개발셋·시험셋 분리**: 설계를 고르는 데 쓴 샘플로 최종 정확도를 말하지 않는다. 비교군(규칙 기반 등)을 같은 조건으로 만들고, 라벨은 **호출 전에 고정**한다. 표본 크기의 한계(1건 = N%p)를 적는다.
- **최종 평가는 한 묶음만** 돌리고, 결과를 보고 고쳐 다시 도는 일을 반복하지 않는다(시험 의존 방지). 개발 중 반복은 개발셋으로만 한다. 비용·시간은 미리 알린다.
- 환경을 임시로 바꾸는 시험(정책 해제·모델 활성화)은 **원래 값을 기록**하고 끝나면 복원·확인한다.
- 실패 사례는 모델의 사유 문구만 보지 말고 **응답 원문의 도구 호출 인자**(길이·잘림·반복)와 오류 응답을 대조한다(원문에만 보이는 증거가 있다).

### G. 구조 한계의 확인
- 도구 정의 기능의 한계(예: 스키마 정리 함수가 `anyOf` 를 접는지)를 코드로 확인한 뒤 설계한다(되는 줄 알고 계획하지 않는다).
- 프레임워크가 요청 필드를 잘라내는 경우(예: `tool_choice`)는 「진짜 강제 불가」로 두고 지침·코드 안전망을 선택한다.

### H. 수정 방식
- 증상마다 문장 하나를 덧붙이지 않는다. 고치기 전에 (a) 교차표의 같은 주제 기존 문장을 보고 (b) 덧붙이기 대신 **기존 문장을 고치거나 지울 수** 있는지 본다.
- **수정이 닿는 범위**: 새로 생성되는 것에만 적용되는가(생성형 지침서는 규칙을 바꿔도 재생성되지 않는다). 이미 있는 것의 방어선은 런타임 지시·도구 설명·오류 문구다.
- **옛 값**(옛 id·참조·지침)이 모델 입력에 남는 경로가 있는가: 매 턴 최신 값을 주입하고, 옛 값을 거절할 때 최신 값의 위치를 알린다.

### I. 효과 확인과 추적
- 수정마다 효과 확인 방법·판정 기준·시점을 **시험 전에** 문서에 적는다. 결정적으로 되는 부분은 단위 시험 단언, 모델이 필요한 부분은 **이미 예정된 시험 묶음에 관찰 항목으로 끼운다**(효과 확인만을 위한 반복 시험을 파지 않는다 — §2-F 「최종 평가는 한 묶음만」과 같은 취지). 확인 전 상태는 「효과 미확인(가설)」이다.
- 점검 중 발견했으나 범위 밖으로 둔 문구·긴장은 「기록만」으로 끝내지 말고 **추적 항목**(위치·왜 문제로 읽히나·재방문 조건)으로 문서의 열린 항목 표 한 곳에 둔다. 예: 한 도구에 「한 번에 모두 호출한다」는 가드가 있는데 다른 절은 대량 데이터를 「나누어 처리한다」고 해 서로 부딪히는 것을 확인하고도 이번 범위 밖이라 관찰만 하고 둔 경우. 다음 점검·수정은 **이 표를 먼저 열어** 같은 계열이면 함께 처리한다. 이전 점검이 적은 범위·한계가 다음 점검의 출발점이다.

## 3. 장치 (이 스킬을 실제로 돌리는 수단)
프로젝트마다 다음을 둔다(그 프로젝트의 지침 문서 — 예: `donghans instr` — 에 위치·실행법을 한 절로 적는다).
1. **입력 덤프 명령**: 한 호출의 최종 입력을 파일로 출력(위 A). 도구·노드 종류(계열)를 인자로 받게 하고, 교차표는 그 출력에서 주제어 검색으로 만든다.
2. **문구 모순 시험**: 코드가 만든 지시 상수끼리의 금지·허용 표현을 단언하는 단위 시험(예: 런타임 지시가 「한 번 더 시도」 같은 모호한 횟수 표현을 쓰지 않는다, 도구 설명에 「한 번만 실행」이 없다).
3. **호환 표 시험**: 모델 ID·추론 파라미터·가격·한도 표에 신규 모델이 있는지 확인하는 시험.
4. **하드 가드와 그림자 판정 로그**: 완료 검증(D)의 차단/그림자 결과를 기록해 오탐률을 본다.
5. **계획서 연결**: `donghans-plan` 의 계획에 「모델이 받는 입력 덤프를 읽었는가」를 점검 항목으로 넣는다.

## 4. 하지 말 것
- 한 모델의 성공 실행으로 「지침이 괜찮다」고 결론내리지 않는다.
- 모델의 사유 문구를 근거로 원인을 **확정**하지 않는다.
- 판단이 필요한 검증을 결정적 가드인 것처럼 문서화하지 않는다(그 반대도).
- 신규 모델 도입을 정책 상수·활성화·과금·호환 중 일부만 확인하고 끝내지 않는다.
- 한 계열의 덤프로 다른 계열의 점검을 끝냈다고 선언하지 않는다.
- 충돌하는 문구를 「이 지시가 우선한다」만 덧대 해소하지 않는다. 어기면 피해가 큰 규칙을 문구로만 두지 않는다(원칙 6).
- 발견한 문제를 「기록만」으로 끝내지 않는다(§2-I).
