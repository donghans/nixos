# donghans-plan — 계획 세우기 → 무맥락 검증 → 구현

과거 대화 기록(ctx)에서 「무맥락 검증」 요청의 상당수가 **계획에 대한 검증**이었다(2026-10-28 조회, 수치는 그 시점 기록에 있고 서브에이전트 브리프가 일부 섞인 대략치였다). 나머지는 이미 쓴 산출물(문서·QA 요청문·푸시 직전 변경)에 대한 검증이었다. 이 스킬은 그때마다 되풀이한 절차를 고정한 것이다. 문서를 읽는 사람이 오해하지 않게 쓰는 방법은 `donghans-doc-rigor` 가 맡고, 여기서는 **구현 전에 계획이 맞는지 확인하는 흐름**을 다룬다.

## 1. 순서 규칙 — 가장 자주 어긴 것
**계획 → 검증 → 정정 → (필요하면 재검증) → 사용자에게 보고 → 구현.** 검증은 구현보다 먼저다.

- **검증 대상을 먼저 정한다.** 「작업하기 전에 검증」「계획 검증」이거나 아직 구현 전이면 대상은 **계획(문서)** 이고 구현을 시작하지 않는다. 이미 쓴 산출물(문서·QA 요청문·푸시 직전 변경)을 가리키면 그 산출물을 검증한다(푸시·전송 전에 한다). 대상이 불명확하면 계획 검증을 먼저 한다.
- 어긴 사례(사용자가 바로잡음): 10-27 「구현을... 지금 해도 돼? 무맥락검증을 해달라한것같은데」, 「아니, 계획파일에 대한 무맥락검증을 해달라한건데...?」, 10-28 「작업하기전에 무맥락검증을 해달라한거야」. 「이것들까지 모두 작업된다면 무맥락검증 진행해줘」(10-27 03:06)의 「작업」은 계획 문서 작업이었고 구현이 아니었다 — 이런 문장은 직전 문맥(계획 문서 작업인지 구현인지)으로 판단하고, 불확실하면 구현 전 검증으로 읽는다.
- 순서가 모호하면 **검증을 먼저** 한다(되돌리기 쉬운 쪽). 구현이 이미 끝난 뒤에 검증을 요청한 것이 분명하면(「작업해주고 … 무맥락 검증」) 그대로 구현 후 검증한다.
- **조건부 허락**(「무맥락 검증이 끝났다면 구현해도 돼」)은 검증과 정정이 끝나고 높음 지적·미결 결정이 없을 때 §4 의 구현 허락을 다시 받지 않고 구현해도 된다는 뜻이다. 검증을 아직 안 했거나 재검증이 필요한 상태면 구현하지 않는다. **허락문에 단서가 붙어 있으면 단서가 우선한다** — 10-27 04:36 「무맥락검증 끝냈다면 구현해도 상관없어(지금 하라는 얘기가 아니라, 문서를 더 다듬을 곳이 한참 남아서)」는 지금 구현하라는 뜻이 아니었다.
- 구현 계획이 일부 구현을 포함해 쪼개져 있어도(예: 도구 먼저 만들고 이관) 순서를 임의로 뒤집지 않는다. 먼저 하고 싶은 부분이 있으면 사용자에게 묻는다.

## 2. 계획을 세울 때
**어디에 두나**: 팀이 읽어야 하는 계획은 저장소의 추적 문서, 개인 작업 계획은 `donghans ctx doc propose plan <이름>`(`donghans-ctx` 스킬). 작은 계획은 대화에서 보여 주는 것으로 충분하고, 검증자에게 줄 때만 스크래치 폴더에 파일로 쓴다(`/tmp` 는 tmpfs 라 재부팅하면 사라진다 — 남길 계획은 `ctx doc propose plan` 으로 옮긴다). 큰 계획은 **인덱스 문서 + 항목별 문서**(예: `plan/repo-restructure/README` + `01-…`)로 나눈다.

**담을 것**
- **배경(사실)**: 검증자가 이 문서만 읽고 알아야 할 현재 상태·관례·근거(§3 에서 배경 설명을 프롬프트에 길게 붙이지 않는 대신 여기에 둔다).
- 목적과 사용자가 확정한 결정(원문 출처 날짜). 하지 않는 것(범위 밖). 알면서 남기는 문제는 「기록만」으로 끝내지 말고 재방문 조건과 함께 열린 항목 표에 둔다(후속 없이 사라지기 쉽다).
- 단계: 순서, 단계별 되돌리는 방법, 검증 방법(시험·`nixup check`·바이트 대조 등), 예상 비용·위험.
- **시험 계획**(계획에 시험을 만드는 단계가 있을 때): 먼저 `donghans-test-judgment` 스킬로 시험마다 판정한다. 표 열은 시험 · 판정(A 장기/B 단기/C 다른 수단/D 안 만듦) · 지키는 결정 한 문장 · 깨지면 피해 · 변이 검사(A) · 끝난 뒤 처리(B: 어디에 기록하나, 바꾼 환경의 복원). 시험이 없는 계획은 「시험 없음 — 이유」 한 줄. 위 「검증 방법」은 단계가 맞는지 확인하는 수단 전반이고, 이 칸은 **저장소에 남길 시험을 고르는 것**이라 겹치면 검증 방법 칸에는 「시험 계획 참조」만 쓴다.
- 열린 결정은 **추천 답과 함께** 한 곳에 모은다.
- 사실은 확인한 것(`파일:줄`·명령·출력)과 추정·미확인을 구분한다(등급은 `donghans-doc-rigor` §1-B).
- **검증 이력 표**(문서 끝): 회차 · 검증자에게 준 판(커밋 해시) · 판정 · 반영한 지적 수 · 날짜. 회차마다 한 줄씩 **추가**한다(고쳐 쓰지 않는다).
- 첫머리에 「**계획이다. 아직 아무것도 바꾸지 않았다**」를 쓴다(「완료」로 읽히는 오독 방지). 구현이 끝나면 완료와 미완을 갱신한다.

**계획을 쓰기 전에** 영향 범위를 전수로 센다: 바꾸려는 이름·경로를 코드·문서·스킬·다른 호스트·추적 제외 파일(`.git/info/exclude`·호스트 로컬 스킬)에서 grep 한다. 검증자가 가장 자주 잡아낸 것이 이 누락이다.

## 3. 무맥락 검증자 띄우기
- **띄우기 전에 수와 모델을 사용자에게 말한다**(전역 CLAUDE.md). 새 일반 서브에이전트를 쓰고 **fork 는 쓰지 않는다**(맥락을 물려받아 무맥락이 아니다). 판단이 필요하므로 sonnet. 작은 계획은 1개, 영역이 둘 이상 갈리는 큰 계획은 영역별 2개를 병렬로(A 구조·이름, B 저장소·운영 식으로).
- **어느 판을 검증했는지 남긴다.** ctx 계획이면 `propose` 가 반영된 것을 `donghans ctx doc status` 로 확인한 뒤(반영은 동기화 담당이 비동기로 한다) 그 판의 커밋 해시를 적는다: `git -C ~/ctx/<프로젝트> log -1 --format=%h -- plan/<이름>.md`(**빈 출력이면 아직 반영 전**이다 — `ctx doc status` 에서 거부·충돌을 확인하고 해결한 뒤 다시). 스크래치 파일이면 `sha256sum` 앞 8자리. 이 값을 검증 이력 표에 넣는다.
- 프롬프트에 **계획서 경로만** 주고 배경 설명을 길게 붙이지 않는다(그래야 모르는 사람이 읽는 상태가 된다). 필요한 사실은 계획서의 「배경(사실)」 절에 둔다.

**프롬프트 틀**(이 순서로 쓴다)
1. 「이전 대화를 모른다고 가정하고 아래 문서만 읽고 시작하세요. 당신은 무맥락 검증자입니다.」
2. 읽기 전용: 저장소·문서를 수정하지 말 것, push·nixup·DB 쓰기·삭제 금지. 허용 범위(임시 폴더에서의 `nix eval`·`cp` 실험 등)가 있으면 명시. 접근 금지 영역(예: 다른 프로젝트의 폴더)은 「확인 불가로 적을 것」.
3. 대상 저장소·브랜치·HEAD, 계획서 경로와 읽을 순서.
4. 점검 항목(아래 1~6(LLM 지침을 바꾸는 계획이면 7 까지, 시험 계획 칸이 있는 계획이면 8 까지, 사용자 발언을 근거로 든 결정·제약·요구가 있는 계획이면 9 까지)의 본문을 **프롬프트에 그대로 붙인다** — 검증자는 이 스킬을 볼 수 없다), 보고 형식(심각도 높/중/낮 · 위치 · 문제 · 근거(실제 확인한 명령·출력) · 권장 수정; 확인 못 한 것은 「확인 불가」), 종합 판정(그대로 신뢰 / 정정 후 신뢰(어디) / 신뢰 불가).
5. 서브에이전트는 `donghans-ctx` 등 스킬을 상속하지 않는다. ctx 조회가 필요한 검증이면 명령(`donghans ctx search … --role user`)을 프롬프트에 적고 읽기 전용임을 명시한다.
6. 마지막에 `git status --short` 를 실행해 저장소를 바꾸지 않았음을 보고하게 한다(검증자가 파일을 만들어 둔 적이 있다).

**점검 항목** — 「실제 구현할 때 막힐 곳」 위주로
1. **자기완결성**: 설명 없이 나오는 용어·선행 참조.
2. **인용 대조**: 계획이 말하는 경로·줄번호·개수·해시를 10~15곳 이상 실제로 열어 대조(추측 금지).
3. **구현 가능성**: 단계를 **손으로 따라가 계산**하게 한다(옮긴 뒤의 상대 경로, import·`sys.path`, 시험 러너의 작업 디렉터리·`python3 -I`, PATH 의존, 빌드 순서, 빠진 단계). 이동·개명 계획의 허점은 대부분 여기서 나온다.
4. **누락·과잉**: 이름·경로 참조처 전수 grep(코드·문서·스킬·다른 호스트). 너무 많이 또는 너무 적게 바꾸는 것은 아닌가.
5. **문서 간 정합성·오독 위험**: 확정/대기/안 하기로 한 것의 서술이 어긋나는지, 계획이 「완료」로 읽히는지.
6. **되돌리기·위험·대안**: 되돌릴 수 없는 단계(삭제·push·DB)가 있는지, 더 나은 대안은 없는지.
7. **(LLM 에게 가는 지침·도구 정의·오류 문구를 바꾸는 계획만) 입력 덤프**: 계획서가 「모델이 실제로 받는 입력 전체」(지침·런타임 지시·도구 설명/스키마·오류 문구)의 덤프를 읽고 쓰였는가, 검증자가 그 덤프를 읽었는가. 덤프가 도구 의미 계열마다인지, 덤프하지 않은 계열이 범위 밖으로 명시됐는지, 범위 밖 항목이 추적 표에 있는지도 본다. 근거 없이 「지침서에 이 문구가 없다」고 결론낸 곳이 없는가(점검 절차는 `donghans-llm-instruction-audit` §2-A·§2-I — 검증자는 이 스킬을 볼 수 없으니 프롬프트에는 참조 대신 위 요구 문장을 그대로 쓴다).
8. **(시험 계획 칸이 있는 계획만) 시험 판단**(A 형 = 저장소에 남겨 계속 돌리는 장기 보호용 시험, B 형 = 지금 한 번 확인하고 버리는 임시 시험, C = 시험이 아닌 다른 수단, D = 안 만듦; 검증자는 이 스킬을 볼 수 없으니 프롬프트에 이 뜻풀이를 함께 붙인다): 시험마다 판정과 「지키는 것 한 문장」이 있는가. A 형에 날짜·시각 고정(상대 날짜가 아님)이나 변이 검사 누락이 없는가. B 형(임시 확인)이 저장소에 새어 들어오지 않는가. 같은 의문에 시험을 반복해 파는 단계가 없는가(두 번째 시험 전에 「예정된 시험에 끼울 수 있나·생략 가능한가」를 적었는가). A 형이 `run-tests.sh` 의 맞는 인터프리터 목록에 등록되는가. 기존 시험을 일괄 정리하는 단계가 끼어 있지 않은가(이 판단은 새 시험에만 쓴다).
9. **(사용자 발언을 근거로 든 결정·제약·요구가 있는 계획만 — 「사용자가 확정한 결정」 표가 있는 계획) 전제 감사** — 아래 「프롬프트에 붙이는 문구」 두 덩어리(본문 + 붙임)를 **그대로** 붙인다. 적용 제외: 한 줄 수정, 사용자 발언에 기대지 않는 순수 기술 계획. 쓰는 법·채점·한계는 이 절 아래 「전제 감사(항목 9) 쓰는 법」.

사용자가 말한 관점은 항목으로 **추가**한다(예: 「너무 많이/적게 정리하는 건 아닌가」, 「기존 데이터 이관과 앞으로의 데이터 생성에서 파편화가 되는가」 — 후자는 별도 한 번 더 돌렸다).

### 전제 감사(항목 9) 쓰는 법
**적용**: 계획서에 「사용자가 확정한 결정」 표가 있거나 사용자 발언을 근거로 든 결정·제약·요구가 있으면 항목 9 를 붙인다. 순수 기술 계획은 붙이지 않는다(읽을 것만 는다). 통합 검증자의 항목이며, 재현율이 낮다고 측정되면 전용 감사관으로 분리한다(미측정 — 아래 「효과」).

**프롬프트에 붙이는 문구**(검증자는 이 스킬을 볼 수 없다. 아래 두 덩어리를 항목 9 로 **그대로** 붙이고 스킬 절 번호·이 스킬 이름은 쓰지 않는다. 합쳐 약 1,017자 — 1,500자 안쪽을 유지한다. 배경·사례는 검증 대상 계획서의 「배경(사실)」 절에 둔다.)
```
9. 전제 감사(사용자 원문 대조): 계획서에서 「사용자가 말했다·정했다·요구했다·불변·필수」에 기대는 문장(전제)을 모두 뽑아 각각 (a) 사용자 원문이 직접 뒷받침 (b) 원문을 해석·확장·일반화 (c) 원문에 근거 없는 에이전트 제안 으로 분류하라. (b)(c) 가 요구·확정 어조로 쓰였거나, 특정 시점·대상에 한정된 발언이 상시 규칙이 되었거나, 「추천대로」「진행해」 같은 포괄 승인이 개별 내용의 확정으로 쓰였으면 지적하라. 설계의 기술적 옳고 그름은 평가하지 않는다. 모르면 「원문에 없음」(키워드 재시도 횟수 병기) 또는 「확인 불가」, 확신이 없으면 (a) 로 쓰지 않는다. 보고는 표: 전제(계획서 위치) | a/b/c | uuid + 원문 복사 인용 + 시각(KST) | 확장·한정 상실 여부.

[원문 읽는 법] ① 후보: `donghans ctx search "<키워드>" --role user --days N --limit M` (`--role user` 를 빼지 말 것. 못 찾으면 「이 키워드로는 못 찾음」이지 「원문에 없음」이 아니다). ② 검색 발췌는 근거가 아니다. 후보마다 `donghans ctx msg <uuid8> --all` 로 전체 본문을 읽고, 인용은 그 출력에서 복사한 것만 쓴다(기억·계획서 속 인용 금지). ③ 본문에 `<pasted_content` 가 있으면 머리·블록·꼬리를 모두 읽는다(요청은 앞·뒤·사이 어디에든). 블록 안 문장은 「붙여넣은 글」로 표시하고 사용자 본인 말로 세지 않는다. ④ 포괄 승인은 (b) 로 분류하고 「위임」+그 승인의 범위 원문을 적는다. ⑤ `<command-*>`·`<bash-input>` 메시지는 인자 부분만 원문이다. ⑥ 원문이 아닌 것: 계획서·인수인계·카드·노트 속 사용자 인용, 서브에이전트 브리프, 「This session is being continued」 요약, 에이전트 응답. ⑦ DB 시각은 UTC 이므로 +9시간 해 KST 로 적는다. ⑧ 원격 저장소가 없는 프로젝트의 원문은 인용 없이 uuid 만 적는다.
```

**입력 필터(사람 발언으로 셀 수 있는 것)**: `ctx search --role user` 가 자동 메시지(`task-notification`·`local-command-*`·`bash-stdout`·`system-reminder` 로 시작, 이어받기 요약)와 서브에이전트 브리프(`is_sidechain`)를 뺀다. `<command-*>`·`<bash-input>`·`<pasted_content>` 는 사람 쪽으로 세므로 위 ③·⑤ 가 따로 필요하다. 한계: 분류는 첫 태그만 보므로 첫 태그가 없고 중간에 자동 태그가 끼었거나 유니코드 공백·BOM 으로 시작하는 자동 메시지는 사람으로 샌다 — 의심스러우면 감사관이 보고한다.

**정본 경로**: 믿는 것은 `ctx msg <uuid> --all` 로 읽은 DB 한 행 전체뿐이다(비밀 치환 적용본, `kind=prompt`·`role=user` 행만 사람 말). 안 믿는 것: 계획서·인수인계·카드·노트 속 인용(에이전트가 쓴 것 — 한 번의 기계 대조에서 55건 중 18건이 원문과 달랐다), `ctx search` 240자 발췌, `ctx session` 기본 출력(1,500자 절단), 에이전트 보고서의 요약·시각, 감사관이 기억으로 쓴 인용.

**호출자가 하는 일(감사관 보고를 채택하기 전, 필수)**:
1. 보고된 인용마다 `ctx msg <uuid> --all` 본문에 대해 인용 일치를 기계로 확인한다 — `ctxaudit check <보고서.md>`(소스 `mods/_tools/llm/llm-ctx/ctxaudit.py`, 시험 대조 채점은 `ctxaudit score --key <정답표.json> <보고서>…`)(공백 정규화 부분 문자열, `…` 조각은 **보고된 순서대로** 나타나야 통과, `<pasted_content>` 블록 안 인용은 별도 표시). 불통과 행은 무효이고 「위조 인용」으로 세어 보고한다. **이 검사는 약하다**: 「위조 0건」은 인용의 존재만 말하고 a/b/c 분류가 맞다는 증명이 아니다(맥락 왜곡·한정 상실은 못 잡는다).
2. 「a」 분류 2~3건은 원문을 직접 읽어 판정한다(§4 의 표본 확인).
3. 보고서를 `ctx doc propose` 로 `remote` 가 있는 프로젝트에 남길 때, remote 없는 프로젝트 대화의 원문 인용은 싣지 않고 uuid 포인터만 쓴다.
4. 포괄 승인(「추천대로」「응」)을 근거로 든 전제는 위임 범위가 원문에 있는지 본다. 감사관 지적을 받아도 사용자 확정으로 격상하지 않는다.

**효과(2026-11-09 기준 미확인)**: 오탐률·재현율은 아직 측정하지 않았다(대조군 시험 자료·채점 도구는 `ctxaudit.py` 와 ctx 파일 `nixos/files/llm-trust/p4-auditor-eval-kit/`(RUNBOOK.md 가 절차) 에 준비됨). 실제 계획서에 쓴 뒤 「지적 행 수」와 「사용자가 맞다고 한 비율」을 기록한다. 시험 전에는 항목 9 의 지적을 **참고**로만 쓰고 단독 결정 근거로 쓰지 않는다.

## 4. 검증 결과 처리
- 코드 리뷰처럼 취급한다. 지적마다 **반영 / 미반영(이유)** 을 정하고 계획서를 고친다. 「참고하겠다」로 흘리지 않는다.
- 검증자의 「맞음」도 표본 한두 곳은 원자료로 직접 확인한다(요약을 그대로 믿지 않는다).
- **재검증**: 정정이 크거나(구조·순서가 바뀜) 높음 지적이 있었으면 다시 돌린다. 재검증 프롬프트에는 「직전 지적은 이미 반영했다. 되풀이하지 말고 (a) 반영 내용이 틀렸거나 실행 불가능한지 (b) 새로 생긴 모순 (c) 아직 못 찾은 막힘만 보고하라」고 쓴다.
- **종료 기준**: 마지막 회차에 높음 지적이 없고 남은 지적을 모두 처리했을 때. 소규모는 1회, 연쇄·운영 인프라 변경은 3~4회까지 간 적이 있다. **최대 4회**로 보고, 그 뒤에도 높음 지적이 남으면 사용자에게 판단을 요청한다. 「정정이 크다」는 순서·구조·범위가 바뀐 경우다(문구·숫자 수정은 재검증하지 않는다). 재검증을 하지 않고 끝냈다면 계획서에 「정정 후 재검증 안 함」이라고 적는다.
- 사용자에게는 **검증 결과(판정·반영한 것·남은 결정과 추천 답·검증 비용)** 를 보고하고, 구현 허락(§1)을 받는다.

### 같은 계획을 여러 번 부를 때 — 판 비교
계획 문서의 버전 관리는 `~/ctx/<프로젝트>/` 의 git 이 한다(반영마다 커밋, 메시지에 `프로젝트/종류/이름 (세션@호스트)`). 전용 명령은 없고 **서버(beelink)에서 읽기 전용으로** git 을 쓴다:
- 이력: `git -C ~/ctx/<프로젝트> log --format='%h %ci %s' -- plan/<이름>.md`
- 두 판 비교: `git -C ~/ctx/<프로젝트> diff <앞 해시> <뒤 해시> -- plan/<이름>.md`
- 그때의 본문: `git -C ~/ctx/<프로젝트> show <해시>:plan/<이름>.md`
재검증 때는 앞 회차 해시와의 diff 를 보고(무엇을 정정했나) 재검증 프롬프트의 「이미 반영한 지적」 목록을 만든다. 저장소는 읽기만 한다(고치는 것은 `propose` 로만). 원격이 없는 프로젝트(ctx 매니페스트의 `remote` 가 빈 곳)는 이력이 서버(beelink)에만 있다.

## 5. 구현할 때
- 검증자가 짚은 「막힐 곳」을 구현 체크리스트로 삼고, 계획의 검증 단계(시험·`nixup check`·대조)를 **실제로 실행**한다. 계획과 달라지면 사용자에게 알린다.
- 되돌릴 수 없는 단계(삭제·push·배포)는 계획에 있어도 사용자 허락 범위를 다시 확인한다.
- 끝나면 계획 문서의 완료/미완을 갱신하고, 커밋 메시지에 어떤 검증 지적을 반영했는지 남긴다.

## 6. 비용 판단
검증자 1개의 시작 비용은 3~4만 토큰이다. 사용자가 요청했거나, 여러 파일·호스트·문서에 걸친 변경, 운영 인프라, 이동·개명·삭제, 되돌리기 비싼 결정이면 한다. 한두 줄 수정은 계획을 대화로 보여 주는 것으로 충분하다. 큰 검증(여러 개·여러 회차) 직전에는 `donghans-limit-watch` 로 한도를 확인한다.

## 7. 실제 예 (2026-10-28, 도구 하나를 다른 폴더로 옮기는 계획)
계획서 한 장 + sonnet 1개로 검증했다. 계획의 핵심(시험이 도구 위치를 계산하는 방식, 시험 러너의 상대 경로, 설정 파일 정리)은 맞았고, 검증자가 **세 가지를 더** 잡았다: ① 계획이 말한 「권한 상승 래퍼」는 대상 도구가 그 기능을 쓰지 않아 불필요(실제 PATH 의존은 다른 명령들), ② 도구 목록 문서의 한 문구도 고쳐야 함, ③ 호스트 로컬 스킬과 다른 호스트에 그 도구 의존이 있는지 확인하는 단계 누락(검증 뒤 각 호스트에서 grep 으로 직접 확인, 참조 없음). 반영한 뒤 구현해 시험 25개·`nixup check` 통과.
