# donghans-limit-watch — 구독 한도 상태와 감시

5h/7d 한도는 **계정 전체 값**이라 모든 세션의 사용분이 합쳐진다. 기록(`~/.local/share/claude-otel/limits.jsonl`)은 어느 세션이든 상태 표시줄이 갱신될 때만 남는다.

## 1. 지금 상태 (큰 작업 직전에 먼저)
```
python3 -I ~/.claude/skills/donghans-limit-watch/scripts/limitwatch.py status [--recent 30] [--json]
```
한 줄: 5h %·리셋 시각·7d %·최근 N분 증가·마지막 기록 시각, 그 아래 최근 구간 비용 상위 세션. 읽기 전용, 바로 끝난다.
- **묻는 선은 플랜별**(출력의 「플랜 … 확인선」 줄이 판정까지 해 준다): `max_5x`·`max_20x` 는 **5h 80%·7d 90%**, pro·알 수 없는 플랜은 70%. 확인선 이상이면 새 큰 작업을 시작하지 말고 사용자에게 묻고, 아래이면 묻지 않고 진행한다(사용자 지시 2026-10-28: max 플랜은 7d 90%·5h 80% 까지 안전). 알림 수준 50/70/80/90% 는 플랜과 무관하게 정보로 알린다.
- 「마지막 기록 N분 전」이 10분 넘으면 그 사이 사용분은 안 보인다(스냅샷). 사용자에게는 「약 N% 이상」으로 말한다.
- 기록이 없거나 못 읽으면 「못 쟀음」이다(종료 코드 1, `--json` 은 `{"error": …}`). 추측하지 않는다 — **70% 확인선으로 간주**하고 사용자에게 못 쟀다고 알린다.

## 1-2. 끝났을 때 몇 %? (큰 작업 직전, `status` 다음에)
`status` 는 **지금** 몇 %인지만 말한다. 큰 작업(병렬 에이전트·긴 시험·대량 작업)은 **끝났을 때** 몇 %일지를 보고 시작할지 정한다:
```
python3 -I ~/.claude/skills/donghans-limit-watch/scripts/limitwatch.py estimate --usd 40 [--duration 90]      # 작업이 쓸 달러(직접 추정)
python3 -I ~/.claude/skills/donghans-limit-watch/scripts/limitwatch.py estimate --agents 6 --per-agent 12    # 에이전트 수 × 단가(단가 기본값 없음)
python3 -I ~/.claude/skills/donghans-limit-watch/scripts/limitwatch.py estimate --minutes 45                  # 이 세션이 지금 속도로 45분 더 쓴다면
```
- 계산: 작업 달러 ÷ 보정값($/p — 5h 1%p 가 몇 달러인가, `limit-calibration.json`) = 5h·7d 증가 %p 범위. 여기에 **다른 세션의 현재 속도**(최근 60분 계정 증가에서 이 세션 몫을 뺀 값)를 작업 시간만큼 더한다. `--duration` 은 작업이 걸릴 분(기본 60 — 다른 세션 속도를 곱할 시간). 현재 세션은 `CLAUDE_CODE_SESSION_ID` 로 알아서 뺀다.
- **달러는 추정해서 준다**: 모르면 비슷한 지난 작업의 비용(`status` 의 최근 구간 비용 상위, `donghans ctx usage`)을 쓴다. 에이전트 1개 단가는 아직 측정 전이라 기본값이 없다 — 모르면 `--usd` 로 거칠게라도 준다. 5 % 안팎의 작은 작업은 정수 % 반올림 때문에 「1~2p」 범위로만 읽는다.
- **판정 3단계**(확인선은 위 `status` 와 같은 플랜별 값, 5h·7d 중 나쁜 쪽): 예상 중앙값이 확인선 아래·범위 상단도 아래면 **진행** / 중앙값은 아래인데 상단이 넘으면 **사용자에게 한 줄 알리고 진행** / 중앙값이 확인선을 넘으면 **묻기** / 이미 현재 값이 확인선 이상이면 묻기(질문에 이 예측을 곁들인다). 확인선 값(80/90 %, pro·불명 70 %) 자체는 바뀌지 않았다. 사용자에게 물을 때는 예상 종료 %·범위와 근거(보정·다른 세션 속도)를 같이 보여 준다.
- **못 쟀음이면 70 % 로 간주**(전역 지침 그대로): 보정이 없는 플랜(현재 max_5x 만 값이 있음. pro·max_20x 는 사용이 쌓이면 보정), 5h 창이 막 리셋돼 기록이 없음, `--minutes` 인데 이 세션 비용 증가가 구간에 없음 등. 종료 코드 1, `--json` 은 `{"error": …}`.
- 출력의 ※ 줄을 읽는다: 기록이 10분 넘게 낡으면 「약 N%」, 구간 기록이 10분 미만·창이 막 시작했으면 다른 세션 합산이 하한뿐, 최근 6시간 비용의 15 % 이상이 opus 면 경고(보정은 sonnet 위주에서만 검증).
- estimate 는 호출할 때마다 **숫자만**(작업 설명·세션 ID·경로 없음) `limit-estimates.jsonl` 에 남긴다. 연습 호출은 `--no-log`. 지난 예측과 실제 비교: `limitwatch.py review` (비교된 예측이 20건 쌓이면 오차 중앙값 ±30 %·범위 안 60 % 이상인지 판정 — 시작값이며 첫 20건을 보고 사용자와 조정).
- 한계: 이 머신의 기록만 본다(다른 머신 사용분은 보정에서는 % 를 크게 예측하는 안전한 쪽, 속도 합산에서는 계정 % 증가에 섞여 들어옴). 달러↔% 비례는 sonnet 위주 22개 창(2026-10-28 이후)에서만 검증됐다. 효과(예측 정확도)는 `review` 가 쌓이기 전까지 **미확인**이다.

## 1-3. 보정 (사람이 가끔, 또는 타이머가)
```
python3 -I ~/.claude/skills/donghans-limit-watch/scripts/limitwatch.py calibrate [--write] [--quiet] [--json]
python3 -I ~/.claude/skills/donghans-limit-watch/scripts/limitwatch.py pin --five 1.9 [--seven 10] [--plan max_5x]   # 손으로 고정(--unpin 으로 해제)
```
- `calibrate` 는 `limits.jsonl` 에서 (계정·플랜별) 5h 창마다 「세션 비용 증가 합 ÷ 창 최고 %」를 구해 중앙값·25/75분위를 낸다. 창 조건: 계정·플랜 필드가 있는 줄만, 창의 첫 5h % ≤ 3·최고 % ≥ 10, 창 시작이 2026-10-28 이후(그 전 기록은 불완전)이고 최근 21일 안. 7d 는 첫 % ≤ 5·증가 ≥ 15p 인 주.
- `--write` 는 5h 창이 8개 이상이고 25/75분위 폭이 중앙값의 50 % 이하일 때만 `~/.local/share/claude-otel/limit-calibration.json` 을 갱신한다(7d 는 주 2개 이상·최대−최소 폭 50 % 이하). 못 맞추면 기존 파일을 두고 이유를 낸다. **`pin` 으로 고정한 값은 자동이 덮어쓰지 않고 `suggest` 칸에만 쓴다.**
- 서버 역할 호스트(llm-ctx)에서는 systemd user 타이머 `limit-calibrate`(하루 1회)가 `calibrate --write --quiet` 를 돈다. 그 밖의 호스트(노트북)는 타이머가 없어 값이 필요하면 손으로 한 번 돌린다.

## 2. 작업 중 감시 (오래 걸리거나 여러 에이전트를 돌릴 때만)
Monitor 로 실행한다(출력 한 줄 = 알림):
```
python3 -I ~/.claude/skills/donghans-limit-watch/scripts/limitwatch.py watch
```
- 시작 때 **현재 상태 한 줄**을 낸다. 과거 기록은 알림으로 재생하지 않는다(옛 감시기는 시작할 때 과거 전체를 「급증」으로 쏟았다).
- 알림 조건: 10분 내 5h +5포인트(`--spike`·`--window`), 5h 50/70/80/90% 첫 도달(`--levels`). 이미 넘은 수준은 다시 울리지 않고, 5h 창이 바뀌면(`resets_at`) 초기화한다. 주간은 +3포인트마다.
- **소진 예측**(`--forecast 150,200`, 빈 값이면 끔): 창 평균 속도(사용률 ÷ 경과)로 리셋까지 외삽한 도달 예측이 150%·200% 에 연속 두 번(5분 격자) 닿으면 「약 N분 뒤 소진」으로 알린다. 창당 단계별 1회. 경과 30분·사용률 10%p 미만이면 외삽하지 않는다(`--forecast-min-elapsed`·`--forecast-min-used`).
- 알림이 오면 사용자에게 알린다. **확인선(플랜별, 위) 이상이면** 하던 일을 멈추고 새 작업을 시작하지 말고 묻는다. 확인선 아래의 알림(50/70% 등)은 알리기만 하고 진행한다. 주간(7d)이 확인선에 처음 닿으면 한 번 알린다.
- Monitor 는 지속 시간에 따라 만료된다. 만료되면 다시 걸어도 시작 때 소음이 나지 않는다.
- 감시는 알림 한 건마다 모델 턴을 쓴다. 짧은 작업엔 `status` 한 번이면 충분하다.

## 한계
- 소진 예측은 2일치(5h 창 9개, 소진 2개)로 시뮬레이션했다. 소진 창 2개는 모두 150% 로 3시간 안팎 전에 잡았고, 오탐 창 1개(최고 50%)가 있었다. 창 평균 속도만 쓰면 200% 단계는 이 기록에서 한 번도 울리지 않는다(짧은 몰아쓰기에 둔감한 대신).
- 급증·수준 기준은 경험칙이며 이 계정의 실측으로 보정한 값이 아니다.
- 기록이 상태 표시줄 갱신에 의존하므로 모든 세션이 멈춰 있으면 값이 갱신되지 않는다.
- 창별 최고 사용률 이력은 `donghans ctx limits`.
- 위 1-2·1-3 의 보정값(5h 1p ≈ $1.7)·판정 3단계는 계획 `plan/llm-trust/05-p3-limit-predict` 의 제안이다. 판정 규칙(D-1)은 계획의 추천(b)을 쓰는 중이며 사용자 확인 전이다.
