## 0. 읽기 전에 (용어)

| 이름 | 뜻 |
|---|---|
| 판정 | `donghans-host-resources` 스킬(`hostmetrics.verdict`)과 usageui 실시간 탭이 내는 「여유/주의/압박/심각」 |
| PSI | `/proc/pressure/*` — 작업이 자원을 기다린 시간 비율. `some`=일부 작업 대기, `full`=그 순간 실행 가능한 작업이 전부 대기. `avg10/60/300`=최근 10·60·300초 평균 |

| 보수적 가용 | 빈 메모리 + 식은(비활성) 파일 캐시. 커널 `MemAvailable` 은 활성 파일 캐시·회수 가능 slab 을 더한 낙관값 |
| 스레셔 | 시험용으로 일부러 메모리를 넘겨 쓰며 스왑을 두드리는 프로세스 |

## 1. 질문(사용자)

「ZRAM 이 가득 찬 건 ZRAM 특성상 상관없는 것 아닌가? 캐시·예약분 같은 형태가 있는지 보고, NVMe 라 속도가 막 못 쓸 정도로 느려지진 않을 것 같다. 실측해 보고 판정을 다시 생각해 보라.」

## 2. 일어난 일(조사·실측 결과)

### 2-1 구성
- ZRAM: `disksize` 15 GiB(압축 전 슬롯), 저장한 원본 13.8 GiB → 압축 후 5.3 GiB, RAM 실제 점유 5.5 GiB(압축률 약 2.6), 알고리즘 zstd, `mem_limit` 없음, 쓰기 백업 장치(`backing_dev`) 없음, 우선순위 100. 슬롯 사용 15559776/15766012 KiB(98.7%). 압축 안 되는 페이지(`huge_pages`) 약 31만 쪽(약 1.2 GiB).
- 디스크 스왑: `/var/lib/swapfile` 24 GiB(우선순위 10, NVMe `SAMSUNG MZVL21T0HCLR`, 회전 없음), 사용 약 15 GiB. 합계 스왑 39 GiB 중 약 30 GiB 사용.
- 해석: 「ZRAM 가득」은 **슬롯(압축 전 기준)이 찼다**는 뜻이지 RAM 을 다 먹었다는 뜻이 아니다. 새로 밀려나는 페이지는 우선순위가 낮은 NVMe 스왑파일로 간다. 이미 ZRAM 에 들어간 페이지는 백업 장치가 없어 NVMe 로 옮겨지지 않고 5.5 GiB RAM 을 계속 차지한다(그래도 13.8 GiB 데이터를 5.5 GiB 에 담았으니 약 8.3 GiB 를 아낀 상태).
- 예약분: `min_free_kbytes` 66 MiB, zone 워터마크 min/low/high 합 0.25/0.28/0.31 GiB(무시할 수준), HugePages 0, CMA 0, cgroup `memory.min/low/high` 설정 없음, THP `madvise`, `swappiness` 60, `page-cluster` 3, overcommit 휴리스틱(Committed_AS 78 GiB > CommitLimit 54 GiB 이나 모드 0 이라 거부 없음). incus VM: win11 약 1.7 GiB, qa-desktop 약 1.9 GiB 사용(후자 한도 8 GiB) — 게스트 RAM 은 호스트에서 `incus.service` cgroup 의 anon+shmem 약 4~5 GiB 로 보이고 게스트 안 캐시는 호스트가 회수할 수 없다.

### 2-2 meminfo 검산
Active+Inactive(anon) 13.97 GiB ≈ AnonPages+Shmem 13.87 GiB(겹침 없음). 총 30.07 − 빈 0.29 − LRU 19.12 = 10.66 GiB 가 slab 2.76 + 페이지테이블 0.38 + ZRAM 5.45 + 약 1.7 GiB 미설명으로 갈라진다. 커널 `MemAvailable` 공식을 필드로 재현하면 6.69 GiB(실제 6.53). 보수적 가용 3.93 GiB.

### 2-3 NVMe 스왑 경로 벤치마크(`mods/_data/claude-skills/donghans-host-resources/scripts/swapbench.py`, cgroup 메모리 300 MiB 제한 안에서 1.5 GiB 사용, 2회 실행 중 완전한 1회)
- 채우기(스왑아웃): 약 315 MiB/s. 순차 읽기(스왑인+동시 스왑아웃): 약 122~124 MiB/s(RAM 상주 대비 약 25배 느림).
- 무작위 한 쪽 접근 지연: p50 48 µs, p90 60 µs, p99 345 µs, p999 2.6 ms, 최대 6.3 ms(RAM 상주 p50 0.3 µs). 초당 약 2만 접근.
- 이 시험 동안 호스트 메모리 PSI avg10 은 최대 약 2.5%, IO some avg10 최대 5%.

### 2-4 다른 프로세스에 주는 영향(`swapbench.py --bystander` 의 프로브, 스레셔 없음 vs 있음, 각 1회·10~14초)
| | 스레셔 없음 | 스레셔(스왑 약 100 MiB/s 양방향) 중 |
|---|---|---|
| sleep(1ms) 초과 p50 / p99 / p999 (µs) | 9.4 / 58 / 133 | 10.1 / 69 / 230 |
| sleep 초과 최대 | 0.45 ms | 3.4 ms |
| 새 메모리 16 MiB 받아 건드리기 p50 / p99 (ms) | 1.32 / 5.9 | 1.40 / 5.5 |
| 같은 시험 최대 | 6.0 ms | 10.7 ms |
→ 한 cgroup 이 스왑을 두드려도 **무관한 프로세스의 지연은 거의 안 변했다**(평균·p99 기준, 최대값은 수 ms 늘어남). 표본 1회이므로 작은 차이는 확정이 아니다.

### 2-5 Netdata 4일 이력(유효 구간만; 앞쪽은 보존 공백이라 0 으로 채워져 있어 제외 — 처음 계산이 이 공백 때문에 틀렸다가 고쳤다)
- 유효 5분 버킷 1142개(2026-10-22 14:35 이후). 낙관 가용 최저 3.3 GiB, 중앙 8.4 GiB. 디스크+ZRAM 스왑 여유 최저 4.8 GiB.
- 메모리 PSI full avg10 ≥1%: 131버킷(11.5%), ≥3%: 31(2.7%), ≥5%: 11(1.0%), ≥10%: 0. full avg60 ≥1%: 25(2.2%), ≥3%: 1. some avg10 ≥10%: 1.
- 현재 판정 규칙 중 「스왑 되읽기 ≥1000 pages/s(약 4 MiB/s)」: 58% 버킷에서 충족(PSI 가 낮으면 「주의」). 보수적 가용 <2 GiB 는 이 4일 동안 낙관값으로도 한 번도 안 닿음.
- full avg10 ≥5% 인 11개 사건 중 2개(10-26 13:05·13:40)는 이 세션의 벤치마크·촬영이 만든 것이다. 나머지 9개(10-23 ×7, 10-24, 10-25)는 사용자의 실제 작업 시간이며 사용자 체감과 대조하지 못했다.

## 3. 판단(이 세션의 해석 — 확정이 아니라 제안의 근거)

1. 현재 기준의 「압박(full avg10 ≥1%)」은 **이 호스트에 과민**하다. 시스템 전체 PSI 는 한 cgroup 이 혼자 스왑을 두드려도 오르지만(스레셔 시험에서 호스트 full avg10 ≈2%), 그때 다른 프로세스는 실질적 영향이 없었다(§2-4).
2. 「ZRAM 거의 가득」은 위험 신호가 아니라 **계층 정보**다(슬롯이 찼고 새 스왑은 NVMe 로 감). 이유 줄에 올릴 일이 아니다.
3. 「보수적 가용 <2 GiB → 주의」는 NVMe 스왑(§2-3, 한 번 접근 약 50 µs)과 큰 스왑 여유 앞에서 실효가 약하다. 이 4일 동안 한 번도 발동하지 않았으니 해가 되진 않지만 의미도 증명되지 않았다.
4. 실제로 **되돌릴 수 없는 한계는 스왑 공간 소진**(OOM)이다. 지금 합계 여유 9.2 GiB(최저 4.8 GiB)라 이 값이 가장 믿을 만한 위험 지표다.
5. 한계: 스레셔는 cgroup 안에 가둔 상황이다. 사용자가 쓰는 앞 창(브라우저·IDE)의 작업집합이 RAM 을 넘을 때의 체감은 측정하지 않았다. 사용자 체감 시각과 이력을 대조하지 않았다. 표본은 대부분 1회다.

## 4. 개정 제안(하기로 한 일이 아니라 사용자 결정 대기)

| 항목 | 현재 | 제안 |
|---|---|---|
| 「ZRAM 거의 가득」 이유 줄 | 있음 | 삭제. 대신 정보 한 줄: 「ZRAM 슬롯 99%·RAM 점유 5.4 GiB(압축률 2.6), 새 스왑은 디스크로」 |
| 보수적 가용 <2 GiB 주의 | 유지 | 제거하거나 「정보」로 강등(표시는 계속) |
| 압박 기준 | full avg10 ≥1% | 지속성을 보는 **avg60**: 주의=full avg60 ≥1%(이력 2.2%), 압박=full avg60 ≥3%(0.1%), avg10 단독 ≥5%는 「순간 튐」 표시(이력 1.0%). 숫자는 4일 이력의 분위이며 **사용자 체감으로 교정 필요** |
| 스왑 되읽기 ≥4 MiB/s 주의 | 58% 버킷에서 발동 | 상향(예: ≥64 MiB/s 이고 PSI 동반) 또는 정보로 강등 |
| 스왑 소진 | 합계 여유 <10% 주의 | **절대값 기준 추가**: 합계 여유 <8 GiB 주의, <3 GiB 압박, <1 GiB 심각(OOM 임박) |
| 누가 대기 중인가 | 없음 | 최상위 cgroup 별 `memory.pressure`(user.slice·system.slice·incus.service 등)의 증가량을 같이 표시해, 한 cgroup 이 만든 압박인지 전체인지 구분 |
| 표시 | 한 단어 판정 | 두 축으로 분리: **속도**(PSI·스왑 지연) / **용량**(스왑 여유) |

교정 방법 제안: 판정을 5분마다 기록(Netdata 에 이미 PSI 가 있으니 별도 수집 불필요)하고, 사용자가 「느꼈던 시각」을 알려 주면 그 시각의 PSI 분위로 임계값을 정한다.

## 6. 범위 밖 / 확인하지 못한 것
- 앞 창 앱이 스왑을 쓸 때의 체감 지연, 전역(제한 없는) 스왑 폭주 시험(다른 세션·VM 에 피해를 줄 수 있어 하지 않음).
- ZRAM `writeback`(백업 장치 연결로 오래된 페이지를 NVMe 로 내리는 방법)과 `zramctl`·`swappiness` 튜닝 효과 — 시험하지 않았다.
- 벤치마크 반복·분산, SSD 수명 영향(쓰기 약 5 GiB 규모로 무시할 수준으로 추정, 미확인).

## 7. 적용 결과 (2026-10-26)

사용자가 §4 의 개정을 승인해 `hostmetrics.py`·`hostres.py`·SKILL.md·usageui 실시간 탭에 적용했다. 시험: `test_hostmetrics.py` 24, `test_usagelive.py` 42 통과(회귀 `test_usage.py` 96 통과).
- 판정 = **속도 축**(메모리 PSI avg60: 주의 full ≥1% 또는 순간 ≥5% / 압박 full ≥3% 또는 some ≥20% / 심각 full ≥10%) 과 **용량 축**(OOM 까지 여유 = MemAvailable + 스왑 여유: <8 / <3 / <1 GiB) 중 높은 쪽. 이유에 [속도]/[용량] 표시.
- 판정에서 뺀 것(「참고」 줄로만): ZRAM 가득, 디스크 스왑 사용량, 스왑 되읽기, 보수적 가용 크기.
- 추가: `psi_cgroups`(메모리 대기를 만든 cgroup, 가장 깊은 쪽으로 좁힘 — 스왑 폭주 시험 중 폭주 scope 가 some 8.7% 로 잡히는 것을 확인), `capacity_guide`(새 작업이 쓸 메모리별 영향 표), `info_lines`.
- **호스트별 스왑 기준점**(사용자 요청: 주력이 아니거나 NVMe 가 아닌 워크스테이션도 있음): `HOST_CALIBRATION` 에 호스트별 벤치마크 실측과 임계값 덮어쓰기를 둔다. 기준점이 없는 호스트에서는 출력에 「스왑 기준점 없음」과 `swapbench.py --bystander --entry` 안내가 뜨고, 스왑이 회전 디스크면(`/proc/self/mountinfo`→`/sys/block/*/queue/rotational`) 경고가 뜬다. `swapbench.py` 가 스킬 폴더로 들어왔고 호스트가 바쁘면(메모리 PSI full avg60 ≥1% 또는 스왑 여유 <4 GiB) 거부한다.
- **2차 실측으로 달라진 해석**: 같은 `swapbench.py` 를 ZRAM 슬롯 약 96%(일부 여유)일 때 다시 돌리자 무작위 접근 p50 이 48 → 7.6 µs 로 크게 낮아졌다(일부가 ZRAM 에 적중), p99 는 345 → 273 µs, 순차 122 → 166 MiB/s. 즉 **p50 은 ZRAM 상태에 따라 변하고 p99(디스크 경로)가 안정적**이라 기준점 항목에 두 번의 값을 함께 적었다. 스레셔 중 타 프로세스 지연도 2차에서 sleep p99 38.0→39.5 µs, 16MiB 할당 p99 6.2→3.0 ms 로 영향이 없음을 다시 확인(n=2).
- 아직 안 한 것: 사용자 체감 시각으로 임계값 교정(§5), 노트북(msi-summit-me)에서의 기준점 측정.
