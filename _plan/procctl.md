# procctl — LLM 에이전트(와 사람)가 쓰는 비대화형 프로세스 정리 CLI — 계획

상태: **구현·시험 완료(단계 A·B·C·D), 새 `claude` 세션에서 권한 규칙 동작도 확인함(2026-10-26, §5) — §2~§4 는 작성 당시 계획이고 실제 결과·달라진 점은 문서 맨 아래 「구현 결과」.** 작성 세션 2026-10-26. 무맥락 검증 1회 거침(§5). 선행: `procui`(대화형 TUI, 구현·배포 완료, 계획·결과는 `_plan/procui.md`). 이 문서는 procui 의 **같은 코어**를 명령줄로 여는 일을 다룬다.

## 0. 읽기 전에 (용어)

| 이름 | 뜻 |
|---|---|
| procui | 프로세스를 그룹으로 보고 골라 종료하는 Textual TUI. 코어는 `mods/_data/procui/` 의 `procscan.py`(스냅샷)·`procgroups.py`(뷰·규칙·필터)·`procactions.py`(보호·계획·pidfd 종료·기록) |
| 보호 | 뷰와 무관하게 프로세스 속성에서 직접 판정하는 종료 금지 규칙. **하드**(PID 1·procui 자신과 조상·커널 스레드·다른 UID)는 풀 수 없고, **소프트**(컴포지터·VM·nix·세션 인프라·LLM 세션 등)는 사람이 이름을 다시 입력해야 풀린다 |
| pidfd | 프로세스 핸들. 핸들을 먼저 얻고 시작 시각을 검증한 뒤 핸들로 신호를 보내면 PID 재사용으로 엉뚱한 프로세스를 죽이지 않는다 |
| 에이전트 | Claude Code 같은 LLM CLI 세션(`SESSION_COMMS`: claude·codex·gemini·opencode, 그리고 NixOS 래퍼가 만드는 프로세스 이름 `.claude-wrapped`) |

## 1. 배경 — 일어난 일

등급: **직접확인**=이 세션이 파일을 읽거나 실행해 확인, **미재확인**=기억·추정.

1. 사용자가 「pkill 같은 일반 사용보다 procui 를 LLM 이 쓰게 하는 것」에 대한 의견을 물었다. 이 세션의 답: TUI 를 LLM 에게 쓰게 하지 말고 **같은 코어의 비대화형 CLI(`procctl`)** 를 만들고, 계획→적용 2단계와 에이전트용 제한을 둔다.
2. 코어에는 이미 필요한 것이 있다(직접확인: `mods/_data/procui/procactions.py`): `PCtx`·`protect_reasons`(보호), `build_plan`(대상·제외·자식 수·예상 메모리), `send`(pidfd 순서: ①`pidfd_open` ②시작 시각 검증 ③신호 직전 새 스냅샷으로 보호 재계산 ④`pidfd_send_signal`), `log`(jsonl, 명령 인자 없음). 이 호스트는 파이썬 3.12(pidfd 가능, 직접확인).
3. LLM 이 `pkill`/`kill` 을 직접 쓸 때의 위험(이 세션의 판단, 미재확인된 사고 사례는 없음): 이름 글롭이 의도보다 넓게 맞는다, 자기 자신·조상(터미널·tmux)이나 다른 세션을 죽인다, PID 재사용, 기록이 없다.
4. Claude Code 는 Bash 명령 패턴별로 허용/확인을 정하는 권한 규칙을 가진다(`update-config` 스킬이 설정 방법을 담음 — 이 세션은 설정 파일을 열어 확인하지 않았다, **미재확인**). 이를 이용하면 「조회·계획은 자동 허용, 적용은 사용자 확인」을 도구가 아니라 하네스에서 강제할 수 있다.

## 2. 하기로 한 일(계획)

### 2.1 명령
- `procctl groups [--view 소유|앱|서비스|세션|<사용자 뷰>] [--filter 식] [--json]` — 그룹·합계(읽기 전용).
- `procctl show <pid|그룹> [--json]` — 세부 사용량·보호 사유(procui 의 상세와 같음).
- `procctl plan [--view V] [--group G] [--filter 식] [--pid N…] [--with-children] [--json]` — **아무것도 죽이지 않고** 계획을 만든다. 출력: 계획 ID, 대상(pid·이름·그룹·시작 시각), 보호로 제외된 것과 사유, 선택하지 않은 자식 수, 예상 확보 메모리. 계획은 `~/.local/state/procui/plans/<id>.json` 에 저장하고 만료 시각(기본 10분)을 둔다.
- `procctl apply <계획 ID> [--term-wait 3]` — 그 계획의 대상에만 SIGTERM, 대기 후 살아남은 목록과 결과를 JSON 으로 낸다. 만료·변조된 계획은 거부. 신호 직전 보호를 새 스냅샷으로 다시 계산(코어의 `send` 가 이미 함).
- `procctl escalate <계획 ID>` — 살아남은 대상에만 SIGKILL(별도 호출 — SIGKILL 이 TERM 과 같은 한 번의 확인에 묻어가지 않게).
- `procctl log [--tail N]` — `actions.jsonl` 조회.
- 종료 코드(계획 당시): 0 성공 · 2 대상 없음 · 3 만료/변조 · 4 보호로 전부 제외 · 5 일부 실패. 구현에서는 2 가 대상 없음·범위 밖·에이전트 상한 초과, 3 이 만료·변조·이미 적용·호출자 권한 거부·없는 계획을 함께 뜻한다.

### 2.2 에이전트 모드(호출자가 LLM 세션이면)
- 판별: 호출 프로세스의 조상 중에 `SESSION_COMMS` 가 있으면 에이전트 모드(환경 변수는 신뢰하지 않음 — 조상은 `/proc` 에서 직접).
- 기본 범위 = **자기 세션의 자식 트리**(자기가 띄운 시험·서버·모니터). 그 밖(다른 세션·사용자의 앱)은 `--scope user` 가 필요하고, 이때도 소프트 보호는 못 푼다.
- **소프트 보호 해제(override)는 에이전트 모드에서 불가능** — 사람이 TUI 에서만.
- 한 번의 apply 대상 상한(기본 20개). 넘으면 거부하고 사용자에게 알리라는 메시지.
- 이름 글롭만으로 곧바로 죽이는 명령은 두지 않는다(반드시 plan → apply).
- 계획 ID 는 호출자가 만든 계획에만 apply 가능(계획 파일에 생성자 pid·시작 시각 기록).

### 2.3 하네스 연동(별도 결정이 필요한 부분 — §3)
- Claude Code 권한 규칙: `procctl groups|show|plan|log` 는 자동 허용, `procctl apply|escalate` 는 **사용자 확인**.
- 지침: `~/nixos/mods/devel/apps/llm-cli.nix` 가 만드는 사용자 지침에 「프로세스 종료는 `pkill`·`killall`·`kill` 대신 `procctl`」 규칙과 스킬(`donghans-procctl`: 사용 순서·종료 코드·보호 사유 읽는 법)을 추가.
- (선택) PreToolUse 훅으로 `pkill`·`killall`·`kill -9` 패턴을 막고 procctl 을 안내.

### 2.4 단계
**단계 A — 코어 정리**: `procactions` 의 계획 직렬화/역직렬화(계획 ID·만료·해시)와 「에이전트 모드 범위」 판정을 코어에 추가. 합격 기준: ①계획 파일을 고쳐 쓰면 apply 가 거부(변조 시험) ②만료된 계획 거부 ③에이전트 범위 밖 pid 는 plan 에서 제외되고 사유가 나옴 ④기존 `test_procui_logic.py` 47개 통과.
**단계 B — CLI**: `procctl.py`(argparse·JSON 출력·종료 코드). 합격 기준: 시험이 `prctl` 로 고유 이름을 붙여 띄운 프로세스만 대상으로 plan→apply→escalate 흐름, 조상·PID 1 은 어떤 옵션으로도 제외, `--json` 스키마 고정.
**단계 C — 설치·지침**: `observe.nix` 에 `procctl` 실행 파일 추가(procui 와 같은 디렉터리·같은 래퍼 방식), 사용자 지침·스킬 문서. 합격 기준: `nixup check --fast` 통과, 적용은 사용자 승인 후.
**단계 D — 문서**: `observe.md` 의 procui 절에 procctl 추가.

## 3. 아직 안 정해진 일(열린 질문)

| 질문 | 기본값(답이 없으면 이대로) |
|---|---|
| 에이전트가 사용자 확인 없이 apply 해도 되는 범위 | **없음** — 모든 apply 는 하네스 권한 규칙으로 사용자 확인(§2.3). 「자기 자식 트리」만 자동 허용하는 완화는 써 본 뒤 결정 |
| 계획 만료 시간 | 10분 |
| apply 대상 상한 | 20개 |
| `pkill` 차단 훅까지 넣을지 | 넣지 않음(지침만) — 우회 사례가 생기면 추가 |
| SIGKILL 정책 | `escalate` 를 별도 명령으로, 에이전트 모드에서는 자기 자식 트리만 |

## 5. 구현 결과 (2026-10-26, beelink-ser7-co 에서 직접 실행·확인)

이 절은 「일어난 일」이다. §2 의 합격 기준은 계획 당시 목표였고 아래가 결과다.

- **구현**: `mods/_data/procui/` 의 `procplan.py`(계획 저장·검증·에이전트 판별) · `procctl.py`(CLI) 신설, 코어(`procactions.send`·`build_plan`·보호)는 그대로 재사용. `observe.nix` 가 `procctl` 실행 파일을 설치(textual 불필요, 기본 파이썬). 스킬 `donghans-procctl`, 사용자 지침(CLAUDE.md 생성부)·`--settings` 권한 규칙·스킬 등록은 `llm-cli.nix`(observe 가 켜진 호스트에서만).
- **시험 `tests/test_procctl.py` 30 통과 / 0 실패(공통 봉투 이전 후 실패 봉투 시험 1건 추가, 이전엔 29)**: plan(대상·보호 제외·범위 밖·만료·서명)·apply·escalate 흐름, 같은 계획 재적용 거부, 계획 파일 변조 거부(바깥 프로세스 생존 확인), 만료 거부, 없는 ID·경로 문자 ID 거부, apply 전 escalate 거부, SIGTERM 무시 프로세스가 살아남은 목록에 남고 escalate 로 종료, 에이전트 기본 범위=자기 세션 자식 트리(바깥 프로세스는 범위 밖), 자기 세션 루트(조상) 지정 시 보호 제외, 에이전트가 사람이 만든 계획 적용 거부, 대상 21개는 에이전트에서 거부(`--scope user` 로도)·사람은 허용, PID 1 제외, override 옵션 없음, groups·show 의 JSON.
- **계획과 달라진 것**: ①소프트 보호 해제 옵션을 에이전트 모드에서만 막는 대신 **CLI 전체에서 아예 제공하지 않음**(사람은 procui) ②에이전트가 `--scope user` 로 넓히는 것은 허용하되 상한 20개는 유지, 권한 규칙이 apply 때 사용자 확인을 강제 ③대상 지정이 전혀 없는 plan 은 거부(전체 선택 없음). ④§3 표의 「SIGKILL 은 에이전트 모드에서 자기 자식 트리만」은 구현하지 않았다 — `check_for_apply` 는 apply 와 escalate 에 같은 범위·상한·권한 규칙을 쓴다(`procplan.py`). ⑤`--scope`·`--ttl`·groups 의 `--sort` 옵션이 추가됐다. ⑥`--json` 은 단순 JSON 이 아니라 공통 봉투(`ctlkit`: `command`·`ok`·`exit_code`·`error`, 결과는 `data`)이고 실패도 같은 봉투다(`donghans-ctl` 스킬). ⑦계획 서명(sig)은 **우발적 수정 감지용**이다 — 같은 UID 의 악의적 위조는 막지 못하고, 실제 안전은 pidfd 재검증과 신호 직전 보호 재계산에서 나온다.
- **하지 않은 것·확인하지 못한 것**: `pkill` 차단 훅(기본값대로 넣지 않음), tmux·ssh 로 감싼 세션에서의 에이전트 판별(조상 사슬 방식이라 동작할 것으로 보나 시험하지 않음).
- **권한 규칙 확인(2026-10-26)**: `nixup` 뒤 새 `claude -p --settings <현재 hooks.json>` 세션에서 `procctl groups --json` 은 승인 없이 실행됐고 `procctl apply …` 는 「권한이 승인되지 않았다」로 막혔다(ask 규칙 동작). 주의: 이미 열려 있던 셸의 `claude` 함수는 옛 `--settings` 경로를 가리켜 규칙이 없었다 — 새 셸에서 시작해야 적용된다.
- **무맥락 검증**: 이 문서는 무맥락 검증 에이전트(2026-10-26, sonnet 1회)를 거쳤고 그 지적(계획 시제 문장·종료 코드·옵션 누락·봉투·서명 한계·시험 개수)을 위처럼 반영했다.
