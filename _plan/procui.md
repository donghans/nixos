# procui — 프로세스 관리 별도 TUI — 계획

상태: **단계 A·B·C·D 구현·시험 완료, 아직 커밋·배포(`nixup` 적용) 전** — 결과는 문서 맨 아래 「구현 결과」. 작성 2026-10-26. 짝 문서: `_plan/usageui-live-tab.md`(usageui 실시간 탭, 선행 작업 「측정 모듈 분리」가 거기 있다).

## 0. 이 문서를 읽기 전에 (용어)

| 이름 | 뜻 |

## 1. 배경 — 일어난 일(조사 이력)

등급: **직접확인**=이 세션이 파일을 읽거나 명령을 실행해 확인, **미재확인**=기억·일반 지식, 확인하지 않음.

1. 사용자 요구: 프로세스 관리에서 **필터링·그룹핑·일괄 닫기·예외 체크·프로세스별 CPU/메모리 사용량과 세부 사용량 확인**이 되는가. 안 되면 별도 UI 로 분리해도 좋다(사용자 지시). 그룹핑은 **「시스템 리소스」와 「내 작업 리소스」 구분을 기본으로 하고, 편의성 구분을 필요할 때마다 추가할 수 있는 형식**이어야 한다(사용자 지시).
2. 기존 도구 조사 — 이 호스트에 설치된 것(직접확인: `which`): btop(`~/.nix-profile/bin/btop`)과 `systemd-cgtop` 만 있다. htop·bottom·glances·atop·zenith·procs·pstree 는 **없다**. 따라서 아래 기능 비교는 설치해 보지 않은 채 기억으로 적은 것이다(**미재확인**).
   - btop: 필터·상세 박스 있음, 여러 개 선택 일괄 종료 없음(하나씩), 이름 단위 그룹핑은 트리뿐.
   - htop: 태그(Space)로 여러 개 선택해 일괄 종료 가능, 이름 단위 그룹핑 없음.
   - bottom(btm): 이름으로 묶어 보고 종료하는 방식이 있는 것으로 앎.
   - 어느 도구에도 「보호(예외) 목록」은 없다고 판단(미재확인). 결론: 요구 전체를 만족하는 기존 도구를 **확인하지 못했다**.
3. usageui 에 이미 있는 것(직접확인): 앱 단위 표(`usageui.py:181` 「앱(전체 프로세스를 앱으로 묶은 합)」)와 프로세스 이름별 표(`usageui.py:183`)가 있으나 저장된 기록을 시간 범위로 집계한 읽기 전용 화면이다. 관리(종료)는 없다. `usageui.py` 머리말에는 프로세스 *관리*(종료·nice)는 btop 에서 하라는 설계 의도가 적혀 있다(직접확인: `mods/_data/observe/usageui.py:5`, 요지 인용).
4. 설계 결정 배경: 모니터(읽기 전용, 안전)와 관리(되돌릴 수 없는 동작)를 **한 UI 에 섞지 않는다.** 섞으면 실수로 누를 위험이 커지고 안전장치를 한곳에 모으기 어렵다(이 세션의 판단, 사용자가 별도 UI 로 분리해도 좋다고 동의).
5. 설치 방식(직접확인): 우리 TUI 는 소스를 store 로 복사하고 `python3.withPackages (ps: [ps.textual])` 로 실행하는 래퍼를 만든다(`mods/sys/services/observe.nix:18-24`). 같은 방식을 쓸 수 있다. 이 환경에 `psutil` 파이썬 모듈은 **없다**(직접확인: `import psutil` → ModuleNotFoundError) — `/proc` 을 직접 읽는다.
6. 기존 코드 재사용 후보(직접확인으로 존재만 확인): `observe_apps.app_name`/`AppResolver`(앱 이름 규칙; electron 앱 이름을 정하려 루트 프로세스의 명령줄을 **읽지만** 저장·표시하지 않음 — 조건에 명령 인자를 쓰지 않는다는 §2.2 규칙과는 별개), hostres 의 `subtree`·`pss_kib`·`session_meta`(자식 트리·PSS·LLM 세션 판별; 단계 0 이후 hostmetrics). **`proc_table` 은 ppid·comm·ticks 만 돌려준다**(검증 에이전트 확인)고 하므로 procui 가 필요한 시작 시각·UID·cgroup·스레드 수는 단계 A 에서 새로 읽어야 한다.
7. 이 호스트의 파이썬은 3.12.13(직접확인) — `os.pidfd_open`·`signal.pidfd_send_signal` 을 쓸 수 있다.

## 2. 하기로 한 일(계획)

### 2.1 목표
`procui`: 터미널에서 프로세스를 **그룹으로 묶어 보고, 필터하고, 여러 개를 골라 안전하게 종료**하며, 프로세스·그룹의 **세부 사용량**을 볼 수 있는 TUI. 모니터가 아니라 **관리 도구**다(실시간 숫자는 보이지만 일차 목적은 선택·조치).

### 2.2 그룹핑 — 「뷰(view)」 단위로 확장 가능하게
- **뷰** = 이름이 붙은 그룹핑 방식 하나. 프로세스 하나가 뷰마다 하나의 그룹 라벨을 갖는다. 화면 위쪽에서 키로 뷰를 순환(`g`)한다.
- 뷰는 **순서 있는 규칙 목록**으로 정의한다. 규칙 = 「조건 → 그룹 이름」, 위에서부터 첫 일치. 조건에 쓸 수 있는 속성: 앱 이름(observe 규칙), 실행 파일 이름(comm·exe), 소유 UID, cgroup 경로 접두어, 부모 조상(예: 어떤 LLM 세션 아래), 메모리/CPU 임계값. **명령 인자는 조건에 쓰지 않는다**(observe 의 개인정보 원칙과 같음).
- 기본 내장 뷰(초안):
  1. **소유(owner)**: 「시스템」(루트·system.slice 서비스·커널) / 「내 작업」(내 UID 이면서 사용자 세션 cgroup 아래) / 「컨테이너·VM」(Docker·incus) — 정확한 경계는 §3 열린 질문.
  2. **앱(app)**: observe 앱 이름 그대로.
  3. **서비스(cgroup)**: systemd 유닛 단위.
  4. **세션(session)**: LLM 세션(claude 등)과 그 자식 트리, 나머지는 「그 외」.
- **사용자 추가 방법**: `~/.config/procui/groups.toml`(없으면 내장 값만 사용). 뷰를 새로 정의하거나 내장 뷰 앞에 규칙을 끼워 넣을 수 있다. 파일은 TOML(파이썬 표준 `tomllib` 로 읽음). 잘못된 규칙은 무시하고 화면 아래 상태줄에 경고(앱이 죽지 않게). 형식 예:
  ```toml
  [[view]]
  name = "작업별"
  [[view.rule]]
  group = "빌드"
  app = ["nix", "cargo", "rustc"]
  [[view.rule]]
  group = "브라우저"
  app = ["vivaldi"]
  ```
- 그룹 행은 펼침/접힘, 합계(CPU %, PSS, 프로세스 수)를 보인다.

### 2.3 필터
- 입력창(`/`)에 이름·앱 부분일치, `cpu>50`, `mem>500M`, `user:me` 같은 간단한 식. 필터 결과는 일괄 선택의 범위가 된다.

### 2.4 선택·일괄 종료와 예외(보호)
- 행/그룹 선택(Space), 필터 결과 전체 선택(`A`), 선택 해제.
- **보호 규칙**: 내장 + `groups.toml` 의 `[protect]`. **보호는 그룹 뷰와 독립으로 계산한다**(뷰 규칙이 잘못 분류돼도 보호가 풀리지 않게 프로세스 속성에서 직접 판정). 내장 기본 — ①procui 자신과 그 모든 조상 프로세스(실행 중인 터미널·쉘·tmux 서버·ssh 세션). **조상은 목록을 만들 때와 신호 직전에 각각 다시 계산**한다 ②PID 1 과 systemd 사용자 관리자 ③컴포지터·패널(hyprland·waybar 등) ④**LLM 세션 프로세스**(경고로 표시하고 기본 제외) ⑤다른 UID 의 프로세스(권한 없음) ⑥incus/qemu VM 프로세스와 docker·containerd 데몬 ⑦진행 중인 `nix`·`nixup` 빌드·배포 프로세스 ⑧세션 인프라(sshd·logind·dbus·pipewire 등)와 observe 수집기. ⑥~⑧ 은 내 UID 의 「내 작업」으로 분류될 수 있어 기본 제외가 필요하다(무맥락 검증 에이전트 지적).
- **그룹 행 종료의 범위**: 그룹 선택은 그 그룹 **구성원 프로세스 전체**이며, 각 구성원의 자식 트리는 자동으로 포함하지 않는다(미리보기에 「자식 K개 별도」로 표시하고 포함 여부를 사용자가 고른다). 부모만 죽여 자식이 재배정되는 경우를 미리보기에서 알아볼 수 있게 한다.
- 보호된 행은 자물쇠 표시, 일괄 선택에서 **기본 제외**. 개별로 강제하려면 별도 확인 대화상자(보호 사유를 보여 주고 이름을 다시 입력).
- **실행 전 미리보기**: 「종료 대상 N개(그룹별), 보호로 제외 M개, 예상 확보 메모리 X」를 목록으로 보여 주고 확인해야 실행.
- **신호 순서**: SIGTERM → 3초 대기 → 아직 살아 있으면 남은 목록을 보여 주고 **다시 물은 뒤** SIGKILL. 처음부터 SIGKILL 은 선택 시에만.
- **PID 재사용 방어(순서 고정)**: ①목록을 만들 때 `/proc/<pid>/stat` 의 시작 시각을 함께 저장 ②신호 직전에 `os.pidfd_open(pid)` 로 핸들을 먼저 얻음 ③그 **다음에** 시작 시각이 저장값과 같은지 검증(핸들을 얻은 뒤 검증해야 확인과 신호 사이 PID 재사용 경쟁이 없다) ④`signal.pidfd_send_signal` 로 핸들에 신호. `os.kill(pid)` 로 대체하지 않는다. pidfd 를 못 쓰는 환경이면 종료 기능을 끈다.
- **기록**: `~/.local/state/procui/actions.jsonl` 에 시각·그룹·comm·PID·신호·결과만 남긴다(명령 인자 미기록).
- 되돌릴 수 없는 동작이므로 **자동화·무확인 모드는 만들지 않는다.**

### 2.5 세부 사용량(상세 창)
- 프로세스 선택 후 Enter: CPU %(최근 구간), PSS/RSS, 스레드 수, 열린 FD 수, 읽기·쓰기 바이트(`/proc/<pid>/io`, 본인 소유만 — 미재확인), cgroup, 시작 시각·가동 시간, 부모/자식 트리, 소속 앱·그룹. 권한이 없는 항목은 「못 쟀음」.
- 그룹 행 Enter: 구성 프로세스 상위 N, 합계.

### 2.6 단계
**단계 A — 순수 로직(UI 없음)**: `procgroups.py`(뷰·규칙 평가·TOML 로딩·검증), `procactions.py`(보호 판정·선택 집합·신호 전송 계획·PID 시작시각 확인·기록). 단위 시험은 실제 시스템 프로세스에 신호를 보내지 않고, 시험이 직접 띄운 `sleep` 자식 프로세스만 대상으로 한다.
- 합격 기준: ①내장 뷰 4개가 **같은 스냅샷** 안에서 모든 프로세스를 정확히 한 그룹에 배정(누락·중복 0; 시험 도중 생기고 죽는 프로세스는 스냅샷에서 고정) ②보호 규칙이 procui 조상·PID 1 을 항상 포함 ③보호 판정이 그룹 뷰를 바꿔도 같은 결과(뷰와 독립), §2.4 보호 ①~⑧ 각각에 해당하는 시험용 프로세스·모의 속성이 일괄 선택에서 빠짐 ④PID 재사용 시뮬레이션(시험이 시작시각을 바꿔 둔 목록)에서 신호가 가지 않음 ⑤잘못된 TOML 에서 예외 없이 경고.

**단계 B — TUI**: `procui.py`(Textual, uikit 사용). 표(그룹 트리), 필터 입력, 선택, 미리보기·확인 대화상자, 상세 창.
- 합격 기준: ①Textual 헤드리스 시험(`App.run_test`)으로 뷰 순환·필터·선택·미리보기 표시 ②시험용 `sleep` 프로세스 그룹을 선택→확인→SIGTERM 으로 종료하고 기록 파일에 남음 ③보호 행이 일괄 선택에서 빠지고 강제 시 별도 확인이 뜸 ④procui 자신의 조상은 어떤 경로로도 종료 목록에 들어가지 않음.

**단계 C — 설치**: `observe.nix` 에 procui 소스 복사 목록·`procui` 실행 파일·런처 항목 추가(hostmetrics 의 복사는 짝 문서 단계 0 이 이미 처리했다고 전제 — 여기서 중복하지 않는다)(위치 선택 이유: 새 모듈은 프리셋 등록이 필요할 수 있어 기존 모듈에 붙이는 쪽이 변경이 작다 — 이 추정은 **미재확인**, 구현 때 `mkMod` 규약 확인 후 별도 모듈로 갈지 결정). observe_apps·uikit 은 기존 복사분을 같은 디렉터리에서 import 한다.
- 합격 기준: `nixup check` 통과(`.build` 사본이 오래될 수 있으니 새로 만든 뒤 확인, 저장소 CLAUDE.md 의 주의), 설치 후 `procui` 가 이 호스트에서 뜸. `nixup`·`rnixup` 적용·재부팅은 이 계획이 허용한 범위가 **아니며** 사용자 승인 후에만 한다.

**단계 D — 문서**: 사용법을 `_docs/content/` 의 해당 문서에 반영(어느 문서가 맞는지는 구현 때 확인).

### 2.7 usageui 와의 관계
- usageui 실시간 탭은 읽기 전용 지표. procui 는 조치. usageui 의 `b` 키(btop 실행, `usageui.py:450`)처럼 usageui 에서 procui 를 여는 키는 **procui 가 안정된 뒤** 추가를 검토(이번 범위 아님).

| 질문 | 기본값(사용자 답이 없으면 이대로 진행) |
|---|---|
| 「내 작업」의 정의. 사용자가 말한 「내 작업 리소스」가 정확히 무엇인지 확인하지 못했다 | 내 UID 이면서 사용자 세션 cgroup(`user@<UID>.service` 또는 `session-*.scope`) 아래 프로세스에서 데스크톱 환경(컴포지터·패널·입력기·알림)을 뺀 것. 그 환경 부분은 「내 환경」 그룹으로 분리. 사용자 의견에 맞춰 규칙으로 쉽게 바꿀 수 있음 |
| LLM 세션을 보호 목록에 기본 포함할지 | 포함(경고 표시, 기본 선택 제외) |
| 설치 위치(observe.nix 에 붙이나 별도 모듈) | observe.nix 에 붙임(§2.6 C 에서 재확인) |
| 사용자 정의 파일 위치 | `~/.config/procui/groups.toml`(nix 로 관리하지 않음 — 사용자가 즉시 고칠 수 있게) |
| `kill` 외 nice 조정 지원 | 1차 범위 밖(종료만). 요청 시 추가 |

## 4. 범위 밖 / 확인하지 못한 것
- 기존 도구(htop·bottom 등)의 실제 기능을 설치해 확인하지 않았다(§1-2).
- 다른 머신·다른 사용자 프로세스 관리, 원격 호스트 대상 관리는 하지 않는다.
- Docker 컨테이너·incus VM **내부** 프로세스는 호스트에서 보이는 만큼만 다룬다. 컨테이너를 어느 세션이 띄웠는지는 알 수 없다(hostres SKILL.md 의 같은 한계).
- 이 계획은 아직 구현·시험하지 않았다. 「합격 기준」은 목표이지 달성 결과가 아니다.
- 저장소에 이 계획과 무관한 미커밋 변경(`mods/devel/apps/llm-cli.nix`)이 있다. 구현 중 건드리거나 함께 커밋하지 않는다.

이 절은 「일어난 일」이다. 위 절들의 「합격 기준」은 계획 당시의 목표였고, 아래가 실제 결과다.

**단계 A — 순수 로직: 완료** — `mods/_data/procui/` 의 `procscan.py`(스냅샷: `start`·uid·cgroup·커널 스레드 표시를 새로 읽음 — 계획대로 `proc_table` 재사용은 안 함) · `procgroups.py`(뷰·규칙·TOML·필터) · `procactions.py`(보호·계획·pidfd 종료·기록).
