# ctxui 대시보드 — 저장소별·계정별 비용 집계 현황과 개선 제안 — 계획

상태: **조사 결과 + 개선 제안(미구현, 사용자 결정 대기).** 작성 2026-10-26. **무맥락 검증(sonnet 1회)을 거쳤고 §2-③·§3-3 의 계정 전제가 틀렸음이 드러나 고쳤다(§6).** 대상: `mods/_data/claude-ctx/ctxdata.py`·`ctxui.py`·`schema.sql`.

## 0. 읽기 전에 (용어)
| 이름 | 뜻 |
|---|---|
| 비용(cost) | `usage_events.cost_usd` 의 합. Claude Code 의 OpenTelemetry 가 요청마다 보고하는 값을 그대로 적재한 것이다. **구독(Pro/Max)에서 이 값이 실제 청구액인지 API 단가 환산 추정인지는 이 저장소의 코드·주석으로 확인하지 못했다**(OTel 값을 그대로 쓸 뿐) — 화면에는 「Claude Code 보고 비용」으로 쓰고 청구액이라고 단정하지 않는다 |
| 분류별(breakdown) | 대시보드의 「분류별」 칸. `g` 키로 모델·저장소·머신·출처·effort 중 하나로 비용을 묶어 보인다 |
| 통계 필터 | 대시보드 맨 위 입력칸 저장소·머신·모델(부분 일치)과 `p` 기간. 통계 칸(추이·분류별·세션 표·한도 그래프)에만 걸린다 |
| 계정 | 구독 계정. 두 곳에 있다: ①OTel 원본의 요청별 속성 `user.account_uuid`·`user.email`(요청마다 100% 있음, 아래 §2-③) ②`limit_samples.account_id`(상태줄 스크립트가 `~/.claude.json` 에서 읽어 남김, 값이 드문드문 NULL) |
| 귀속 | 어떤 사용 기록(요청)이 어느 저장소·계정의 것인지 정하는 일. **저장소는 `sessions` 조인으로 정확히 정해지고**, 계정은 아래 §2-③ 처럼 방법에 따라 정확하기도 추정이기도 하다 |

## 1. 질문(사용자, 2026-10-26)
①저장소별로 쓴 비용 집계가 되나 ②세션 통계에서 저장소별 필터를 걸 수 있나 ③계정별로도 금액 집계가 가능한가 ④이렇게 했을 때 더 나은 대시보드 출력 방법이 있나(있으면 무맥락 검증).

## 2. 일어난 일(조사 결과 — 실제 DB 를 집계로만 읽음, 내용 비열람, 2026-10-26)
등급: **직접확인** = 이 세션이 코드를 읽고 실제 DB 에 조회해 얻은 값.
- **①저장소별 비용: 된다(직접확인).** `usage_breakdown(by="repo")` = 대시보드 「분류별」에서 `g` 로 「저장소」를 고르면 나온다(기본은 모델별). 실제 DB: 총 $723.57·요청 16,088 중 ToT $433.49 · genple $139.98 · nixos $138.59 · shopify-dk-sync $10.02 · (저장소 없음) $1.49. 단점: **기본 화면에 안 보이고(모델별이 기본), 저장소별 표(왼쪽 위)에는 비용 열이 없다**(세션·메시지·프롬프트·텍스트·용량만).
- **②세션 통계의 저장소 필터: 된다(직접확인).** 맨 위 「저장소(통계)」 입력(부분 일치, ILIKE)이 추이·분류별·세션 표·세션 통계에 걸린다. **한도 그래프에는 기간(`days`)과 머신(`host`)만 걸리고 저장소·모델은 안 걸린다**(`limit_windows(days, host)`, ctxui.py:895 — 한도는 계정 단위라 당연하지만 화면에 안 적혀 있다). 합계 일치를 확인: `repo=nixos` 세션 표 비용합 $138.59 = 추이 합 $138.59, `repo=genple` $139.98 = $139.98 — **단 `usage_events` 가 10-22 이후 4일치뿐이라 30일 창과 전체가 같아서 맞는 것**이다(세션 표 비용은 세션의 전체 기간 비용이고 기간 필터는 `s.last_ts` 로 세션을 고르므로, 기간이 짧거나 데이터가 쌓이면 추이 합과 어긋날 수 있다). 한계: ①위쪽 「전체·표별 용량」·저장소별 표는 이 필터의 영향을 받지 않는다 ②부분 일치라 `x` 처럼 짧으면 여러 저장소가 걸린다 ③저장소별 표에서 Enter 는 **검색 탭으로** 가며 통계 필터를 채우지 않는다.
- **③계정별 비용: `usage_events`/`limit_samples` 로는 안 되지만, OTel 원본으로는 정확히 된다(직접확인 + 검증 에이전트 재현).**
  - `usage_events` 에는 계정 열이 없고(열: request_id·host·ts·session_id·prompt_id·model·토큰·cost_usd·duration_ms·query_source·effort·speed), `limit_samples` 는 11,935행 중 계정이 있는 것이 796건뿐이다(계정이 찍힌 세션 8개, 그 8개에도 NULL 행이 섞여 있음 — 상태줄의 `~/.claude.json` 읽기가 가끔 실패하는 것으로 의심되나 원인 미확인). 세션→계정을 `limit_samples` 로 이으면 $723 중 **$62(8.6%)만 귀속**된다.
  - **그러나 OTel 원본(`~/.local/share/claude-otel/events.jsonl`)의 `claude_code.api_request` 15,341건 모두에 `user.account_uuid`·`user.email`·`user.account_id`·`organization.id` 속성이 있다**(누락 0, 이 세션이 직접 확인). 계정은 **2개**: `262407eb…` 13,200건·$621.27 / `2d82354e…` 2,141건·$77.71(11%). 수집 코드(`claude_ctx.py:262-272`)가 이 속성을 읽지 않아 DB 로 안 들어왔을 뿐이다.
  - 검증 에이전트 확인: 원본 기준 78개 세션 중 **2개는 세션 도중 계정이 바뀌었다** — 세션 단위 최빈 귀속은 그 비용을 한 계정으로 몰아 틀린다.
  - 이 원본은 **beelink 의 것**이라 노트북(msi-summit-me) 사용분(약 $26.5)은 포함되지 않는다(노트북은 자기 OTel 파일을 자기 쪽에서 적재; `limit_samples` 247행은 전부 계정 NULL).
- **④현재 대시보드의 불편(직접확인, 화면 촬영)**: 비용을 보려면 `g` 로 바꿔야 한다 · 저장소별 표에 비용이 없다 · 계정은 한도 그래프에만 있고 금액과 연결되지 않는다 · 「비용」이 구독 사용자에게는 환산 추정치라는 설명이 화면에 없다(`HELP_TERMS` 에도 없음).

## 3. 개선 제안(결정 전 — 하기로 한 일이 아니다)
1. **저장소별 표에 「비용」「비중」 열 추가** — 같은 표에서 세션·메시지·비용을 같이 본다(`overview()` 의 저장소 집계에 `usage_events` 를 저장소로 조인). 통계 기간 `p` 와 맞출지가 결정 사항(§5-2).
2. **「비용 상위」 고정 칸** — 분류별을 `g` 로 바꾸지 않아도 항상 보이는 「저장소별 비용 상위 5 + 합계」 막대(트랙 막대, usageui 와 같은 방식). 분류별은 그대로 둔다.
3. **계정 분류 추가 — 수집 시점에 정확한 계정을 `usage_events` 에 넣는다**(검증 에이전트 제안 채택): ①`schema.sql` 에 `ADD COLUMN IF NOT EXISTS account_id text, account_email text`(기존 패턴) ②수집(`claude_ctx.py` 파서)에서 `user.account_uuid`·`user.email` 한 줄씩 읽어 적재 ③**과거는 `events.jsonl` 재처리로 백필**(`ON CONFLICT DO NOTHING` → 계정 열만 `DO UPDATE`; 실제 사실이라 추정이 아님. DB 를 바꾸는 일이라 사용자 허가 후) ④`BREAKDOWNS` 에 「계정」 추가(이메일 라벨; 제한 모드에서는 기존 한도 그래프와 같은 치환 규칙) ⑤계정이 없는 행(노트북분 등 원본이 없는 호스트)은 「(계정 불명)」 행으로 그대로 보이고 제목에 불명 비율을 적는다.
4. **저장소 행에서 통계 필터 걸기 키** — 저장소별 표에서 한 키(예 `f`)로 위 「저장소(통계)」 입력을 그 저장소로 채우고 통계 칸을 갱신한다(Enter 는 지금처럼 검색).
5. **「환산 비용」 명시** — 비용이 나오는 칸 제목·도움말에 「API 단가 환산 추정, 구독이면 실제 청구 아님」.
6. **기간별 합계 한 줄** — 오늘·7일·30일 합계를 한 줄(통계 상태줄 근처)에 둔다.
- 하지 않을 것(제안): `limit_samples` 로 세션→계정을 추정(최빈 귀속)하는 방식 — 세션 중 계정이 바뀐 사례가 이미 있어 틀린 숫자를 만든다.
- 구현 함정(검증 에이전트): 제안 1 의 저장소 집계(`overview`)는 `sessions LEFT JOIN messages` 에 `count(...)` 를 쓰므로 `usage_events` 를 바로 조인하면 **행이 곱해져 메시지 수·용량이 부풀어 오른다** — 세션별로 먼저 집계한 서브쿼리로 붙인다. 제안 1(비용 열)과 2(고정 칸)는 같은 정보라 하나로 합치는 편이 낫다(저장소별 표에 열을 넣고 고정 칸은 두지 않거나, 반대).

## 4. 위험·함정
- 노트북 사용분: 이 호스트에 원본이 없어 계정이 비는 행이 남는다 → 「(계정 불명)」으로 정직하게 보이고, 노트북이 같은 수집 코드로 적재하면(`nixup` 후 새 행부터) 채워진다. 노트북 쪽 과거 원본의 백필은 그 호스트에서 별도로 해야 한다.
- 계정 이메일을 DB 평문에 두는 것은 `limit_samples` 와 같은 수준이다. 제한 모드(LLM 세션)의 화면에서 이메일을 치환할지는 기존 한도 그래프 처리를 따른다(결정 필요).
- 저장소 부분 일치 필터(ILIKE)는 `x`·`a` 같은 입력에 넓게 걸린다 — 표시된 저장소 수를 제목에 적는다.
- 「비용」이 청구액인지는 미확인(§0) — 구독이면 실제 청구와 다를 수 있으니 「Claude Code 보고 비용」으로 표기.
- 한도 그래프에는 저장소·모델 필터가 안 걸린다(계정 단위) — 화면에 표기.
- 제안 1 의 비용 열 기간(통계 기간 `p`)과 같은 표의 세션·메시지 열(전체 기간)이 어긋난다 → 열 제목에 기간 표기.

## 5. 열린 결정 (추천 답 — 모두 에이전트 제안)
1. 제안 1~6 중 무엇을 → 추천: 1(저장소별 표 비용 열, 서브쿼리 조인)·4·5·6 은 작고 안전, **3(계정)은 수집 시점 계정 열 + 백필**로 함께. 2(고정 칸)는 1 과 중복이라 생략.
2. **DB 스키마 변경과 백필 허가** → 추천: 허가(열 추가 후 `events.jsonl` 재처리, 계정 열만 갱신, 되돌리려면 열 삭제). 백필 전에 건수만 먼저 보고한다.
3. 비용 열 기간 → 추천: 통계 기간 `p`(기본 30일)에 맞추고 열 제목에 기간 표기.
4. 제한 모드에서 계정 이메일 → 추천: 기존 한도 그래프와 같은 규칙.
5. 노트북 과거 분 → 추천: 노트북에서 같은 백필을 따로(이번 범위 밖).

## 6. 무맥락 검증 반영 (2026-10-26, sonnet 1회)
- **뒤집힌 것**: 「과거 계정은 알 수 없다·계정 1개뿐」은 틀렸다 — OTel 원본에 요청별 계정이 있고 계정은 2개($621/$78). 이 세션이 직접 재확인했다. §2-③·§3-3·§4 를 고쳤다.
- 정정: 한도 그래프의 필터 범위, 합계 일치가 4일치 데이터 덕에 맞는 것, 세션 수 분모(`usage_events` 155 vs `sessions` 153 — 12개 세션은 `sessions` 행이 없어 「(저장소 없음)」으로 감), 「상태줄이 갱신될 때마다」가 아니라 값 키(5h%·7d%·비용·세션)가 바뀔 때만 기록(`claude-usage-statusline:37-40`), `limit_samples` 의 계정 시작 시점(문서의 10-23 이 아니라 대부분 10-24 03시 이후·10-26 01시 이후).
- 숫자 재현: 총 비용 $723.89(문서 $723.57, 수집 진행으로 증가)·저장소별·귀속 비용 8.6% 일치.
- **검증이 확인하지 못한 것**: 구독에서 `cost_usd` 의 의미(§0), `limit_samples` 계정 NULL 의 원인, 노트북 사용분의 계정, 윈도 조인 성능(대안 채택으로 불필요).
