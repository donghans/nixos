## 결론

커널 안 eBPF 집계(제로베이스 후보)의 정확성과 비용 — 정확하지만 bpftrace 구현은 상시용으로 비쌈

## 상세

**커널 안 eBPF 집계(제로베이스 후보)의 정확성과 비용 — 정확하지만 bpftrace 구현은 상시용으로 비쌈**: ① 정확성: 프로세스(tgid)별 자발 전환을 `sched_switch` 에서 직접 세면 `/proc` 모든 스레드 합과 **중앙값 99%**(15개 프로세스, 범위 96~139%; 139% 는 이미 끝난 스레드의 카운터가 `/proc` 에서 사라지는 차이 — eBPF 가 더 정확), on-CPU 시간은 `/proc/<pid>/stat` 과 **101%**.
② 비용(`bpftool prog show`, `kernel.bpf_stats_enabled=1` 을 잠깐 켬, 끝나고 0 으로 원복): `sched_switch` 프로그램 **호출당 5,949 ns × 3,022/s ≈ 코어 1개의 1.8%**, 문맥 전환 수에 비례(빌드 중 3만/s 이면 약 18%) — bpftrace 의 해시맵 4회 갱신 때문.
비교: 현재 수집기(30초 간격, 스레드까지 읽기)는 약 0.5%이고 부하에 따라 늘지 않음

## 근거(조건)

정확성은 두 스냅샷을 eBPF 부착·종료 시점에 맞춰 0.1초 안에 찍고(처음에 셸 반복문으로 해서 간격이 길어져 eBPF 가 60% 로 보인 오류가 있었음 — 스냅샷이 느리면 비율이 일정하게 틀어진다) 각각 자기 간격으로 나눔. 교차 출처 일치도: 같은 구간 psys 가 observectl 11.63 W 대 Netdata 11.55 W, 패키지 4.69 대 4.65 W

## 수준을 올리려면

**정정(같은 날 실제 운영에서 발견): 정수 Hz 샘플링의 에일리어싱** — 19Hz 단계를 실제 수집기에 올려 기본 수집(`/proc` stat)과 대조하니 **netdata 가 3.2배(5개 간격 2.9~3.4배)** 로 나왔다(전체 합은 일치 — 프로세스별 배분만 편향). 19Hz 는 1초 주기 작업과 정수비라 위상이 고정돼 한쪽 위상만 계속 찍힌다(앞의 20초 실험 '중앙값 95%' 는 위상이 우연히 어긋난 한 번의 결과였다). **비조화 주기 53,711µs(1/(18+0.618…)초)로 바꾼 뒤**: netdata 1.09배(0.78~1.29), electron 0.93, apps.plugin 1.05, **전체 중앙값 0.99**(같은 이름의 프로세스는 합쳐서 비교; vivaldi 0.61 은 저장이 상위 16행뿐이라 일부가 빠진 탓). 교훈: 주기 샘플링은 대상의 주기와 정수비가 아니게. 결론: **상시 eBPF 집계는 지금은 채택하지 않는다**(코어 1.8%+부하 비례). 후보: libbpf 로 per-CPU 배열 맵을 쓰는 C/Rust 집계기(호출당 수백 ns 목표)를 만들면 상시가 가능하나 개발·유지 비용이 큼 → T23. 당분간은 30초 L0(스레드 정확) + 필요할 때 `observectl bpf`(요청형) + 분석 구간만 5초 L1
